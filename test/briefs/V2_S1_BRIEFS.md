## 1편 `v1-next-token` — AI는 글을 어떻게 만들까? · 다음 토큰 예측과 온도

- 제목: AI는 글을 어떻게 만들까?
- 부제: 다음 토큰 예측과 온도
- summary: 같은 질문에도 AI의 답이 매번 조금씩 다른 이유는 고장이 아니라 "다음 조각을 확률로 뽑는" 방식 때문이에요. 온도와 샘플링, 그리고 2026년에 온도 손잡이가 잠긴 이야기까지 담았어요.
- keywords: 다음 토큰 예측, 토큰, 확률 분포, 온도, temperature, 샘플링, top-p, 뉴클리어스 샘플링, 사전학습

핵심 주장: 언어 모델은 사전학습에서 "앞 문맥이 주어졌을 때 다음 조각(토큰)"을 예측하도록 배워요. 답을 만들 때는 매번 다음 토큰 후보의 확률 분포를 만들고 그중 하나를 뽑아 이어 붙여요. 온도는 이 분포를 뾰족하게(1등만) 또는 평평하게(낮은 후보도) 만드는 손잡이예요. 늘 1등만 고르면 단조롭고 반복되기 쉬워서, 상위 후보 안에서 뽑는 샘플링(top-p)이 쓰여요. 2026년의 최신 모델들은 이 손잡이를 사용자가 바꾸지 못하게 잠그거나 기본값 유지를 권해요. 그래서 "일관된 답"은 온도가 아니라 프롬프트(형식·예시)로 잡아요.

### 확인된 사실

1. 사전학습된 자기회귀 언어 모델은 "문서 안의 앞 문맥이 주어졌을 때 다음 단어를 예측"하도록 학습돼요. 이렇게 사전학습만 된 모델은 질문에 답하거나 지시를 따르는 데 능하지 않아서 미세조정과 RLHF로 다듬어요. — Claude 용어집(Pretraining) https://platform.claude.com/docs/en/about-claude/glossary (날짜 표기 없음 / 확인 2026-10-02)
2. 온도(temperature)는 생성 중 예측의 무작위성을 조절해요. 높으면 더 다양하고 창의적인 출력, 낮으면 가장 확률 높은 표현을 고르는 보수적인 출력이 나와요. 온도를 0으로 해도 완전히 결정적이지 않아서 같은 입력에 다른 출력이 나올 수 있다고 밝혀요. — 같은 Claude 용어집(Temperature)
3. "온도 0은 결정적이어서 항상 가장 확률 높은 응답이 선택된다." topK 1은 가장 확률 높은 토큰을 고르는 탐욕적 디코딩(greedy decoding). topP 예시: 토큰 A·B·C의 확률이 0.3·0.2·0.1이고 topP가 0.5면 A나 B 중에서 온도를 써서 고르고 C는 후보에서 빠져요. — Gemini API 문서 Prompt design strategies https://ai.google.dev/gemini-api/docs/prompting-strategies (날짜 표기 없음 / 확인 2026-10-02)
4. (2026 흐름) 같은 Gemini 문서: Gemini 3.x 모델은 이 파라미터들을 기본값으로 둘 것을 강하게 권하고, 온도를 1.0 아래로 내리면 반복 루프(looping)나 성능 저하 같은 예상치 못한 동작이 생길 수 있다고 밝혀요.
5. (2026 흐름) Claude Opus 4.7 이후 모델(Opus 5.5 포함)은 temperature·top_p·top_k를 기본값 외로 설정하면 요청을 거부(400 오류)해요. 문서는 "프롬프팅으로 모델의 행동을 이끌라"고 안내해요. — Migrating to Claude Opus 5.5 https://platform.claude.com/docs/en/models/opus-5-5/migration-guide (날짜 표기 없음 / 확인 2026-10-02). Messages API 레퍼런스에도 "Claude Opus 4.6 이후 출시 모델은 temperature 설정을 지원하지 않으며 1.0만 하위 호환으로 받는다"는 Deprecated 표시가 있어요. — https://platform.claude.com/docs/en/api/messages/create
6. 가능도(likelihood)가 가장 높은 쪽을 고르는 디코딩(탐욕·빔 서치)은 단조롭고 반복적인 글을 만들고, 확률 분포의 상위 "핵(nucleus)"에서 뽑는 뉴클리어스 샘플링(top-p)이 사람 글에 더 가까운 품질을 낸다. — Holtzman 외, The Curious Case of Neural Text Degeneration, arXiv 1904.09751 (2019.4.22 제출, ICLR 2020) https://arxiv.org/abs/1904.09751
7. 한 단어씩 출력하도록 학습됐는데도, Claude가 운율 있는 시를 쓸 때 줄 끝에 올 운(rhyme) 단어를 먼저 떠올려 두고 그곳에 닿도록 줄을 쓰는 "미리 계획"이 관찰됐어요. — Anthropic, Tracing the thoughts of a large language model (2025-03-27) https://www.anthropic.com/research/tracing-thoughts-language-model

확인 불가: OpenAI API의 temperature 범위(403). 온도의 수식(소프트맥스를 T로 나누기)은 이번에 연 1차 문서에 식으로 나오지 않았어요. 자막에는 "분포를 뾰족하게/평평하게"까지만, 만져 보기 코드 안에서만 소프트맥스(logit/T)를 써요.

### 장면 초안

1. 사례: 같은 질문, 세 가지 답 (13초)
   - 자막: "가을 소풍 안내문 첫 문장 써 줘." 같은 질문을 세 번 했더니 세 번 다 다른 문장이 나왔어요. / 하나는 "가을 하늘 아래", 하나는 "설레는 소풍 날". 고장 난 걸까요?
   - 무대: 같은 질문 상자 1개 + 답 말풍선 3개가 차례로 뜸(문장만 다르고 형식은 비슷). 쿼카 think 포즈.
2. 원리: 한 조각씩 확률로 이어 붙여요 (14초)
   - 자막: AI는 문장을 통째로 쓰지 않아요. 앞 문맥을 보고 <em>다음 토큰</em>(글 조각) 후보마다 확률을 매겨요. / 그중 하나를 뽑아 붙이고, 그 문장을 다시 보고 또 다음 조각을 뽑아요. 사전학습에서 배운 일이 바로 이 "다음 조각 맞히기"예요.
   - 무대: "우리 반 소풍은 ___" 상자 → 후보 칩 5개와 확률 막대(예: 내일 .40 / 다음 .25 / 가을 .15 / 비 .12 / 취소 .08, 예시값) → 하나 선택 → 문장에 붙는 화살표 반복 2회.
3. 온도: 분포를 뾰족하게, 평평하게 (13초)
   - 자막: <em>온도</em>는 이 확률 막대의 모양을 바꾸는 손잡이예요. 낮추면 1등만 커지고, 높이면 낮은 후보도 뽑힐 기회가 생겨요. / 늘 1등만 고르면 글이 단조롭고 같은 말이 반복되기 쉬워서, 상위 후보 안에서 뽑는 방식(top-p)을 써요. 2019년 연구가 이걸 보였어요.
   - 무대: 막대 5개가 온도 낮음(한 막대만 높음) ↔ 높음(고르게) 사이를 tick으로 오감. 칩 "온도 낮음: 늘 비슷" / "온도 높음: 다양하지만 엉뚱할 수도".
4. 2026년: 손잡이가 잠기는 중 (13초)
   - 자막: 그런데 2026년의 최신 모델들은 이 손잡이를 잠그는 쪽으로 가고 있어요. 한 회사는 기본값 말고는 아예 거부하고, 다른 회사는 1.0 아래로 내리면 같은 말을 되풀이할 수 있다며 기본값을 권해요. / 그래서 "늘 같은 형식"이 필요하면 온도 대신 <em>형식과 예시</em>를 프롬프트에 적어요. 온도 0도 완전히 똑같은 답을 보장하진 않았어요.
   - 무대: 잠긴 다이얼 그림(P.box + 자물쇠 대신 P.ICON.key) → 화살표 → "형식 + 예시" 상자. 칩 "온도 0 ≠ 항상 같은 답".
5. 정리: 뽑기지만, 앞을 내다보기도 해요 (13초)
   - 자막: 한 조각씩 뽑는다고 아무 생각 없이 이어 붙이는 건 아니에요. 2025년 해석 연구에서는 시를 쓸 때 줄 끝의 운 단어를 먼저 정해 두는 모습이 관찰됐어요. / 같은 질문에 답이 다르게 나오는 건 고장이 아니라 확률로 뽑기 때문이에요. 안내문처럼 형식이 정해진 글은 형식과 예시로 고정해요.
   - 무대: 시 두 줄(운 단어 두 개를 오렌지 칩으로 먼저 띄운 뒤 줄이 채워짐). 쿼카 wave.

### 만져 보기 "다음 토큰 뽑기 기계"

- "우리 반 소풍은 ___" 문장과 후보 6개(고정 logit 값). 온도 range(0~2, step 0.1) → 소프트맥스(logit/T) 막대가 즉시 바뀜(온도 0은 1등 100%로 처리). top-p 체크박스(0.9) → 누적 확률 밖 후보는 회색.
- primary 버튼 "다섯 번 뽑기": `P.rng(42 + 누른 횟수)`로 결정적 샘플 5개를 뽑아 문장 5개 표시. 같은 온도에서 다시 열면 같은 결과.
- 아래 고정 문구: "예시 확률이에요. 실제 모델은 수만 개 토큰에 확률을 매겨요." 첫 range 최대(2.0)에서 막대가 평평해져 DOM 변화.

### tip
- body: 가정통신문·공문처럼 형식이 정해진 글은 "세 문장, 첫 문장은 날짜와 장소" 같은 형식 지시와 예시 한 편을 같이 주세요. 온도를 못 바꾸는 최신 모델에서도 결과가 안정돼요.
- extra: 반대로 아이디어가 여러 개 필요하면 "서로 다른 안 다섯 개"를 한 번에 요청해 보세요. 뽑기를 여러 번 돌린 효과가 나요.

### myth
- myth: 온도를 0으로 하면 언제나 똑같은 답이 나온다.
- fact: 온도 0은 늘 가장 확률 높은 조각을 고르게 하지만, 실제 서비스에서는 같은 입력에도 출력이 달라질 수 있다고 공식 문서가 밝혀요. 그리고 2026년 최신 모델 일부는 온도 자체를 바꿀 수 없어요.

## 2편 `v1-context` — 긴 대화에서 AI는 왜 앞 내용을 잊을까? · 토큰·컨텍스트 창·컴팩션

- 제목: 긴 대화에서 AI는 왜 앞 내용을 잊을까?
- 부제: 토큰, 컨텍스트 창, 컴팩션
- summary: 대화가 길어지면 AI가 학년을 되물어요. 토큰이 쌓이는 "책상" 컨텍스트 창, 넘칠 때 앞부분을 요약본으로 바꾸는 컴팩션, 그리고 대화 밖에 따로 적어 두는 메모리까지 3분에.
- keywords: 토큰, 컨텍스트 창, context window, 작업 기억, 컨텍스트 로트, 컴팩션, compaction, 메모리, Lost in the Middle

핵심 주장: 모델은 컨텍스트 창(작업 기억) 안의 토큰만 보고 답해요. 시스템 프롬프트, 올린 파일·이미지, 지금까지의 대화, AI의 답과 생각 토큰까지 전부 이 창을 차지해요. 2026년에는 창이 100만 토큰까지 커졌지만, 길수록 회상 정확도가 떨어지는 "컨텍스트 로트"가 있어요. 넘칠 때는 앞부분을 밀어내거나, 요약본으로 바꿔 끼우는 컴팩션을 써요. 메모리는 창 밖에 따로 적어 두는 메모장이라 별개의 장치예요.

### 확인된 사실

1. 컨텍스트 창은 모델이 응답을 만들 때 참조할 수 있는 모든 텍스트(응답 자신 포함)이고, 학습 데이터와 달리 모델의 "작업 기억"이에요. 토큰이 늘수록 정확도와 회상이 떨어지는 현상을 context rot이라 부르고, 그래서 무엇을 넣느냐가 공간 크기만큼 중요하다고 밝혀요. — Claude 문서 Context windows https://platform.claude.com/docs/en/build-with-claude/context-windows (날짜 표기 없음 / 확인 2026-10-02)
2. 같은 문서: 요청 안의 모든 것이 창을 차지해요. 시스템 프롬프트, messages 안의 모든 메시지(도구 결과·이미지·문서 포함), 도구 정의, 그리고 그 턴에 생성한 출력과 확장 사고까지요.
3. 같은 문서: Claude Opus 5.5·Sonnet 5.5·Opus 4.6 등 목록의 모델은 100만 토큰 창이고, Sonnet 4.5 등 다른 모델은 20만 토큰이에요. claude.ai 같은 채팅 화면은 창을 "먼저 들어온 것부터 내보내는(FIFO)" 방식으로 관리할 수도 있다는 각주가 있어요.
4. (2026 흐름) 컴팩션은 대화의 오래된 턴을 Claude가 서버에서 쓴 요약으로 바꿔 끼워 긴 대화를 창 안에 유지하고, 대화가 길어질수록 응답 품질이 떨어지기 때문에 활성 컨텍스트를 작게 유지해요. 기본 요약이 나중 턴에 필요한 걸 빠뜨리면 요약 지시문을 직접 쓰라고 안내해요. — Claude 문서 Compaction overview https://platform.claude.com/docs/en/build-with-claude/compaction (온디맨드 컴팩션 베타 헤더 `compact-2026-09-04` / 확인 2026-10-02)
5. (2026 흐름) claude.ai에서는 대화가 창 한계에 가까워지면 "이전 메시지를 요약해 대화를 이어 가고", 그때 "organizing its thoughts(생각을 정리하는 중)"가 보일 수 있으며, 자동 컨텍스트 관리에는 코드 실행이 켜져 있어야 해요. 유료 요금제의 최신 모델은 최대 100만 토큰 창이라고 밝혀요. — Claude 고객지원 How do usage and length limits work? https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work (날짜 표기 없음 / 확인 2026-10-02)
6. 컴팩션은 "창 한계에 가까운 대화를 요약해 새 창을 그 요약으로 다시 시작하는 것"이고, 지나친 컴팩션은 나중에야 중요성이 드러나는 미묘한 맥락을 잃을 수 있어요. 트랜스포머는 토큰 n개에 대해 n² 쌍의 관계를 다뤄야 해서 길수록 주의가 얇아진다고 설명해요. NOTES.md 같은 외부 메모로 창 밖에 정보를 남기는 방법도 소개해요. — Anthropic Engineering, Effective context engineering for AI agents (2025-09-29) https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
7. 긴 문맥에서 관련 정보가 처음이나 끝에 있을 때 성능이 가장 높고, 가운데 있을 때 크게 떨어져요. — Liu 외, Lost in the Middle, arXiv 2307.03172 (2023.7.6 제출, TACL) https://arxiv.org/abs/2307.03172
8. Claude 기준 토큰 하나는 영어 약 3.5글자이고, 정확한 수는 언어에 따라 달라져요. — Claude 용어집(Tokens) https://platform.claude.com/docs/en/about-claude/glossary
9. (2026 흐름) 메모리: 2026-03-02 무료 사용자까지 "대화 기록 기반 메모리" 제공, 2026-07-10 하루 단위 요약 대신 "주제별 개별 항목"으로 개편, 2026-08-25 채팅과 Cowork에 걸쳐 작동하고 설정의 Topics에서 항목을 고치거나 지울 수 있으며 "민감한 주제 포함" 설정이 추가됐어요. — Claude 고객지원 Release notes https://support.claude.com/en/articles/12138966-release-notes (확인 2026-10-02)
10. 메모리는 대화하면서 개별 주제로 저장되고, 건강·정치적 신념 같은 민감한 주제는 기본적으로 저장하지 않으며, 신분증 번호·범죄 경력·금융 계좌 번호·체류 자격은 요청해도 저장하지 않아요. 시크릿(incognito) 대화는 메모리와 검색 대상에서 빠져요. 채팅 검색은 요청할 때만 과거 대화를 RAG로 찾아와요. — Claude 고객지원 Use Claude's chat search and memory https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context (날짜 표기 없음 / 확인 2026-10-02)

확인 불가: "한국어는 영어보다 더 잘게 쪼개진다"(1차 출처 못 찾음). 기존 e5의 해당 자막과 대본 문장은 "토큰 수는 언어에 따라 달라져요"로 바꿔요.

### 장면 초안

1. 사례: "아까 말한 학년이 뭐였죠?" (13초) — 기존 e5 장면 1 그대로 재사용(대화 카운터 30).
   - 자막: 연수 자료를 만들며 AI와 서른 번쯤 주고받았어요. / 그런데 AI가 되물어요. "아까 말씀하신 학년이 뭐였죠?"
2. 토큰과 책상 (13초)
   - 자막: AI에게 글은 <em>토큰</em>이라는 조각으로 들어가요. 영어는 대략 서너 글자에 하나, 다른 언어는 비율이 달라져요. / 이 토큰이 쌓이는 곳이 <em>컨텍스트 창</em>, AI의 작업 기억이에요. 책상이라고 생각하면 쉬워요.
   - 무대: 문장 → 토큰 칩(기존 e5 장면 2 재사용, "대략적인 예시" 문구 유지) → 칩이 책상 상자로 들어감.
3. 책상에 올라가는 것은 대화만이 아니에요 (13초)
   - 자막: 책상에는 내 질문만 올라가지 않아요. 앱이 미리 넣은 지시문, 올린 파일과 사진, AI의 답, AI가 속으로 한 생각까지 다 올라가요. / 2026년엔 책상이 100만 토큰까지 커졌지만, 많이 쌓일수록 정확히 떠올리는 힘이 떨어져요. 이걸 컨텍스트 로트라고 불러요.
   - 무대: 책상 상자 안에 칩 묶음 5종(지시문·파일·사진·대화·생각)이 차례로 쌓이고, 오른쪽에 "많을수록 흐려져요" 막대(진한→옅은).
4. 넘치면: 밀어내기와 컴팩션 (14초)
   - 자막: 책상이 차면 오래된 것부터 밀어내거나, 앞부분을 <em>요약본으로 바꿔 끼워요</em>. 이걸 컴팩션이라고 해요. / 채팅 화면에 "생각을 정리하는 중"이 뜨면 이 요약이 돌아가는 중이에요. 다만 요약에서 빠진 세부는 다시 볼 수 없고, 가운데 놓인 내용은 원래도 놓치기 쉬워요.
   - 무대: 왼쪽 대화 칩 10개 → 앞 7개가 접혀 "요약" 칩 1개로 바뀌는 애니메이션(tick). 요약 칩 옆 회색 칩 "5학년"이 사라지는 연출(빠진 세부). 오른쪽 작은 "앞·중간·뒤" 칩 줄(가운데 오렌지).
5. 메모리는 책상 옆 메모장이에요 (13초)
   - 자막: <em>메모리</em>는 책상과 따로 있는 메모장이에요. 대화하면서 "5학년 담임" 같은 항목을 적어 두고, 설정에서 보고 지울 수 있어요. 건강 같은 민감한 주제는 기본으로 적지 않아요. / 그래도 지금 작업의 핵심 조건은 마지막 메시지에 한 번 더 적고, 긴 작업은 요약 메모를 만들어 새 대화에서 이어 가요.
   - 무대: 책상(컨텍스트 창) 상자 옆에 메모장 상자(항목 칩 3개), 그 아래 "핵심 조건은 마지막에 다시" 말풍선. 쿼카 idea.

### 만져 보기 "책상과 컴팩션 시뮬레이터"

- 기존 e5 만져 보기(토큰 칩 분해기 + 책상 크기 슬라이더)를 살리되, 분해기 안내문에서 한국어 비율 언급을 빼고 "실제 토큰 수는 모델의 토크나이저가 정해요"로.

- 아래 "메모리에 적기" 보조 버튼: 학년 항목을 메모장 칸에 고정해 컴팩션 뒤에도 남는 걸 보여 줌.

## 3편 `v1-prompt-parts` — 좋은 질문은 무엇으로 이루어질까? · 역할·맥락·형식·예시

- 제목: 좋은 질문은 무엇으로 이루어질까?
- 부제: 역할, 맥락, 형식, 예시(퓨샷)
- summary: "가정통신문 써 줘" 한 줄과, 역할·맥락·형식·예시 네 조각을 갖춘 질문은 결과가 달라요. 각 조각이 모델 안에서 무슨 일을 하는지 공식 가이드와 연구로 짚어요.
- keywords: 프롬프트, 역할, system 메시지, 맥락, 형식, 예시, 퓨샷, few-shot, 인컨텍스트 학습, XML 태그

핵심 주장: 모델은 프롬프트 안의 정보만으로 일을 해요(1·2편). 그래서 ① 역할(system 메시지 한 문장으로도 말투·관점이 바뀜) ② 맥락과 이유(왜 그래야 하는지 알려 주면 규칙을 일반화) ③ 형식("하지 마"보다 "이렇게 해") ④ 예시(퓨샷: 형식·말투·구조를 가장 확실히 잡음)를 채워 줘요. 예시는 내용이 정답인지보다 형식과 범위를 보여 주는 효과가 크다는 연구가 있어요. 2026년 공식 가이드들은 예시를 "항상 넣으라", "3~5개"라고 권해요.

### 확인된 사실

1. "Claude를 맥락을 모르는 똑똑한 신입 직원으로 생각하라." 황금률: 과제 맥락을 모르는 동료에게 프롬프트를 보여 주고 따라 할 수 있는지 물어보라. — Claude 문서 Prompting best practices https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (날짜 표기 없음 / 확인 2026-10-02)
2. 같은 문서: 지시의 맥락이나 이유를 알려 주면 목표를 더 잘 이해해요. 예: "말줄임표 쓰지 마" 대신 "응답을 음성 합성 엔진이 읽으니 말줄임표를 쓰지 마"가 더 효과적이고, 모델이 설명에서 일반화한다고 밝혀요.
3. 같은 문서: 예시는 출력 형식·말투·구조를 이끄는 가장 믿을 만한 방법이며(퓨샷/멀티샷), 관련성 있고 다양하며 `<example>` 태그로 구분하라. "최선의 결과를 위해 예시 3~5개를 넣으라."
4. 같은 문서: system 프롬프트로 역할을 정하면 행동과 말투가 그 용도에 맞춰지고 "한 문장만으로도 차이가 난다." 형식은 "하지 말 것" 대신 "할 것"을 말하라(예: "마크다운 쓰지 마" 대신 "매끄러운 산문 문단으로 써"). 긴 자료는 위에, 질문은 끝에 두면 테스트에서 응답 품질이 최대 30% 좋아졌다고 밝혀요.
5. (2026 흐름) 같은 문서: Claude 4.6 이후 모델은 마지막 assistant 턴을 미리 채워 형식을 강제하는 프리필을 받지 않아요(400 오류). 형식은 지시문, 구조화 출력, XML 태그로 잡으라고 안내해요.
6. (2026 흐름) "프롬프트에 항상 퓨샷 예시를 넣기를 권한다. 예시 없는 프롬프트는 덜 효과적일 가능성이 크다." 예시들의 구조와 서식을 같게 맞추라. 문제를 푸는 데 필요한 정보를 모델이 이미 안다고 가정하지 말고 프롬프트에 넣으라. 응답 형식(표, 목록, 문단 등)을 지정할 수 있다. — Gemini API Prompt design strategies https://ai.google.dev/gemini-api/docs/prompting-strategies (확인 2026-10-02)
7. GPT-3(1,750억 파라미터)는 미세조정이나 가중치 업데이트 없이 텍스트로 준 몇 개의 예시만으로 새 과제를 수행했어요(인컨텍스트 학습). — Brown 외, Language Models are Few-Shot Learners, arXiv 2005.14165 (2020.5.28 제출) https://arxiv.org/abs/2005.14165
8. 예시 속 정답 라벨을 무작위로 바꿔도 성능이 거의 떨어지지 않았고, 성능을 좌우한 건 라벨의 범위, 입력 글의 분포, 형식이었어요. — Min 외, Rethinking the Role of Demonstrations, arXiv 2202.12837 (EMNLP 2022) https://arxiv.org/abs/2202.12837

### 장면 초안

1. 사례: 한 줄 프롬프트 (13초)
   - 자막: "가정통신문 써 줘." 결과는 어느 학교, 어느 학년에도 붙일 수 있는 밋밋한 글이었어요. / AI가 모르는 게 너무 많았던 거예요. 공식 가이드는 AI를 "맥락을 모르는 똑똑한 신입"이라고 불러요.
   - 무대: 한 줄 프롬프트 상자 → 회색 일반 문단 상자. 쿼카 oops.
2. 조각 1: 역할 (13초)
   - 자막: 첫 조각은 <em>역할</em>이에요. "너는 초등 3학년 담임이야" 한 문장이면 단어 고르는 기준이 바뀌어요. / 앱 뒤에서는 이 문장이 <em>system 메시지</em>라는 칸에 들어가요. 대화 맨 앞에 깔리는 지시문이에요.
   - 무대: system 칸(ink) + user 칸(aqua) 두 줄 구조 도식. 역할 칩.
3. 조각 2: 맥락과 이유 (13초)
   - 자막: 두 번째는 <em>맥락</em>이에요. 날짜, 대상, 준비물처럼 AI가 알 수 없는 사실을 넣어요. / 이유까지 쓰면 더 좋아요. "학부모 대부분이 휴대폰으로 읽으니 세 줄로" 하면, 세 줄 규칙을 다른 데에도 알아서 적용해요.
   - 무대: 맥락 칩 4개(10월 17일·3학년·도시락·우천 시) + "왜?" 말풍선.
4. 조각 3: 형식 — "하지 마" 대신 "이렇게" (13초)
   - 자막: 세 번째는 <em>형식</em>이에요. "길게 쓰지 마"보다 "세 문장, 첫 문장은 날짜와 장소"가 잘 먹혀요. / 하지 말라는 말은 무엇을 하라는지 알려 주지 않거든요. 긴 자료는 위에, 질문은 맨 끝에 두는 것도 형식이에요.
   - 무대: 왼쪽 X 상자 "길게 쓰지 마" / 오른쪽 체크 상자 "세 문장: 날짜·장소 → 준비물 → 문의". 
5. 조각 4: 예시(퓨샷), 그리고 네 조각 (14초)
   - 자막: 마지막은 <em>예시</em>예요. 작년 안내문 한두 편을 붙이면 말투와 구조가 가장 확실히 잡혀요. 이걸 퓨샷이라고 불러요. / 2022년 연구에서는 예시 내용이 틀려도 성능이 크게 안 떨어졌어요. 모델이 예시에서 주로 배우는 건 <em>형식과 범위</em>라는 뜻이에요. 역할, 맥락, 형식, 예시. 네 조각을 채워요.
   - 무대: 네 조각 카드 2×2(역할 ink / 맥락 aqua / 형식 orange / 예시 aqua). 쿼카 wave.

### 만져 보기 "네 조각 프롬프트 조립기"

- 체크박스 4개(역할·맥락·형식·예시)와 각 조각의 고정 문구. 위 칸에 조립된 프롬프트를 실시간 표시(system 칸과 user 칸으로 나눠 보여 줌).
- 오른쪽 "예시 결과" 칸: 켜진 조각 조합(16가지)마다 미리 써 둔 결과 문단을 결정적으로 표시하고, 아래에 "이 조각이 바꾼 것" 한 줄(예: 형식 켬 → "세 문장 구조가 생겼어요").
- primary 버튼 "네 조각 다 넣기": 네 개를 모두 켜고 결과가 바뀜. "예시 답변이에요" 고정 문구.

## 4편 `v1-hallucination` — AI는 왜 그럴듯하게 틀릴까? · 할루시네이션과 '찍기' 보상

- 제목: AI는 왜 그럴듯하게 틀릴까?
- 부제: 할루시네이션과 '찍기'를 보상하는 채점
- summary: AI는 모르는 것도 자신 있게 답해요. 2025년 연구는 그 이유를 두 가지로 설명해요. 한 번만 본 사실은 맞힐 수 없고, 채점 방식이 "모르겠다"보다 찍기를 더 높이 쳐 준다는 것이에요.
- keywords: 할루시네이션, 환각, 그럴듯함, 사전학습, 싱글턴, 평가, 벤치마크, 찍기, 기권, 확신 임계값

핵심 주장: 할루시네이션은 그럴듯하지만 사실이 아닌 내용을 만드는 것이에요. 2025년 연구에 따르면 ① 사전학습만으로도 오류는 통계적으로 생겨요. 학습 데이터에 오류가 없어도 그래요. 특히 데이터에 딱 한 번 나온 사실(생일 같은 임의의 사실)은 패턴이 없어 맞히기 어려워요. ② 학습 뒤에도 사라지지 않는 이유는 평가가 맞으면 1점, 틀리거나 "모르겠다"면 0점인 이진 채점이라서 찍는 쪽이 점수가 높기 때문이에요. 해법으로 "확신이 t 이상일 때만 답하라, 틀리면 감점"을 채점에 명시하자고 제안해요. 거짓말(의도)이 아니라 확률과 채점이 만든 행동이에요.

### 확인된 사실

1. 언어 모델이 불확실할 때 인정하는 대신 그럴듯한 오답을 내는 이유는 훈련·평가 절차가 불확실함을 인정하기보다 추측을 보상하기 때문이라고 주장해요. 모델은 "좋은 시험 응시자"가 되도록 최적화되고, 불확실할 때 찍으면 점수가 오른다. 새 평가를 더 만들기보다 리더보드를 지배하는 기존 벤치마크의 채점을 고치자고 제안해요. — Kalai, Nachum, Vempala, Zhang, Why Language Models Hallucinate, arXiv 2509.04664 (2025-09-04 제출) https://arxiv.org/abs/2509.04664
2. 같은 논문 본문: "학습 데이터에 오류가 없어도, 사전학습에서 최소화하는 통계적 목표는 오류를 내는 모델로 이어진다." 생성 오류율은 "이게 맞는 출력인가?"를 가리는 이진 분류(Is-It-Valid) 오분류율의 약 2배 이상이라는 관계를 보여요. — https://arxiv.org/html/2509.04664
3. 같은 본문: 패턴이 없는 임의의 사실은 학습 데이터에 딱 한 번 나온 비율(싱글턴 비율)만큼은 틀린다. 예: 생일 사실의 20%가 사전학습 데이터에 딱 한 번 나오면, 기본 모델은 생일 사실의 적어도 20%에서 할루시네이션을 낼 것으로 예상된다.
4. 같은 본문: 저자(Adam Kalai)의 생일을 묻자 DeepSeek-V3가 "03-07", "15-06", "01-01"처럼 서로 다른 답을 냈고(정답은 가을), 박사논문 제목도 세 모델이 서로 다른 지어낸 제목을 냈어요. "DEEPSEEK에 D가 몇 개?"에는 열 번 시도에서 2나 3이라고 답했어요.
5. 같은 본문: 시험 비유 — "불확실할 때 학생은 객관식에서 찍고, 서술형에서도 자신 없는 그럴듯한 답을 쓴다." 대표 벤치마크(GPQA, MMLU-Pro, BBH, SWE-bench 등)는 이진 채점이고 "모르겠다"에 점수를 주지 않아요(WildBench만 부분 점수).
6. 같은 본문의 제안: "확신이 t보다 클 때만 답하라. 틀리면 t/(1−t)점 감점, 맞으면 1점, '모르겠다'는 0점." 예: t=0.5면 감점 1, t=0.75면 감점 2, t=0.9면 감점 9.
7. 할루시네이션 정의: "그럴듯하지만 사실이 아닌 내용(plausible yet nonfactual content)". — Huang 외, A Survey on Hallucination in Large Language Models, arXiv 2311.05232 (2023.11.9 제출, ACM TOIS 게재 승인) https://arxiv.org/abs/2311.05232
8. 정직한 AI는 정확한 정보를 주고 할루시네이션을 내지 않으며 적절할 때 한계와 불확실성을 인정한다(HHH 프레임워크). — Claude 용어집(HHH) https://platform.claude.com/docs/en/about-claude/glossary

확인 불가: OpenAI 블로그의 모델별 기권율·오답률 표(403). 자막에 특정 상용 모델의 할루시네이션 비율을 쓰지 마세요.

기존 e4에서 가져올 것: 장면 4 "거짓말이 아니라 패턴" 구도, 장면 5 할 일 카드(숫자·날짜·고유명사는 1차 출처, 이미지 속 숫자는 쓰지 않기). e4의 영상 프레임 에셋(423ppm→420ppm)은 사례로 짧게 재사용 가능.

### 장면 초안

1. 사례: 세 번 물으니 세 번 다른 생일 (13초)
   - 자막: 한 연구자가 AI에게 자기 생일을 물었어요. 3월 7일, 6월 15일, 1월 1일. 답이 매번 달랐고, 셋 다 틀렸어요. / 말투는 늘 자신 있었어요. 왜 "모르겠어요"라고 하지 않을까요?
   - 무대: 같은 질문 상자 + 날짜 칩 3개(오렌지) + "정답: 가을" 회색 칩. 쿼카 think. (자막에 "2025년 연구 논문에 실린 실제 사례예요" 추가 가능)
2. 이유 1: 한 번 본 사실은 맞힐 수 없어요 (14초)
   - 자막: AI는 많이 본 패턴은 잘 맞혀요. 그런데 생일처럼 규칙 없이 그냥 외워야 하는 사실이 학습 자료에 <em>딱 한 번</em>만 나왔다면요? / 2025년 연구는 그런 사실의 비율만큼은 틀린다고 계산했어요. 한 번만 나온 생일이 20%라면, 적어도 20%는 지어낸다는 거예요.
   - 무대: 사실 카드 10장(8장은 여러 번 겹쳐 진하게, 2장은 한 장뿐이라 흐리게) → 흐린 2장에 물음표. "20%" 큰 글씨.
3. 이유 2: 채점이 찍기를 보상해요 (13초)
   - 자막: 학습이 끝난 뒤에도 안 사라지는 이유가 있어요. AI를 평가하는 시험 대부분이 맞으면 1점, 틀려도 "모르겠어요"라고 해도 <em>0점</em>이에요. / 그러면 찍는 쪽이 늘 점수가 높아요. 객관식에서 빈칸으로 내는 학생이 없는 것과 같아요.
   - 무대: 채점표 두 열(찍는 AI vs 솔직한 AI), 10문항 중 확신 낮은 4문항에서 찍는 AI가 1문항 맞혀 총점이 더 높게 나옴.
4. 해법 제안: 틀리면 감점 (13초)
   - 자막: 연구진의 제안은 채점 규칙을 바꾸는 거예요. "75% 이상 확신할 때만 답하세요. 틀리면 2점 감점이에요." / 이렇게 하면 모를 때는 "모르겠어요"가 이득이 돼요. 시험지에 감점 규칙을 미리 적어 두는 것과 같아요.
   - 무대: 같은 채점표에 감점 규칙 적용 → 순위가 뒤집힘. 칩 "확신 75% · 오답 −2".
5. 거짓말이 아니라 확률과 채점, 그래서 할 일 (14초)
   - 자막: 그래서 할루시네이션은 속이려는 거짓말이 아니라, 확률로 빈칸을 채우고 찍기가 보상받은 결과예요. / 숫자·날짜·사람 이름은 1차 출처로 확인하고, 질문할 때 "확실하지 않으면 모른다고 답해 줘, 근거도 붙여 줘"라고 채점 규칙을 먼저 알려 주세요.
   - 무대: 할 일 카드 3개(1차 출처 확인 / "모르면 모른다고" 요청 / 근거 요구). 쿼카 wave.

### 만져 보기 "채점 규칙 바꾸기"

- 10문항, 각 문항에 고정 확신도(예: .95, .9, .85, .8, .7, .6, .5, .4, .3, .2)와 정답 여부를 결정적으로 정함(확신도 높은 문항일수록 정답).
- AI 두 명: "늘 찍는 AI"(전부 답함), "솔직한 AI"(확신도 < 임계값이면 "모르겠어요").
- 채점 방식 라디오: 이진 채점 / 감점 채점. range "확신 임계값 t"(0.5~0.9) → 감점 t/(1−t)를 표시하고 점수 재계산.
- primary 버튼 "감점 채점으로 바꾸기": 점수표와 순위가 뒤집혀 DOM 변화. "예시 문항이에요" 고정 문구.

### teacherLines
- "AI는 모를 때도 <b>찍는 게 점수가 더 높게</b> 배워 왔어요. 그래서 자신 있게 틀려요."
- "AI에게 물을 땐 <b>'확실하지 않으면 모른다고 해 줘'</b>라고 먼저 말해 줘요."

### tip
- body: 숫자·날짜·사람 이름·법 조항은 1차 출처로 다시 확인하세요. 질문 끝에 "확실하지 않은 부분은 모른다고 표시하고, 근거가 있는 문장에는 출처를 붙여 줘"를 붙이면 지어낸 답이 눈에 띄게 드러나요.
- extra: 생일, 개교일, 특정인의 논문 제목처럼 규칙 없이 외워야 하는 사실이 할루시네이션이 가장 잦은 곳이에요. 이런 질문은 처음부터 검색이나 자료 첨부(5편)와 함께 하세요.

### myth
- myth: AI가 일부러 거짓말을 한다.
- fact: 속이려는 의도가 아니라, 한 번만 본 사실을 확률로 채우고 "모르겠다"보다 찍기가 점수를 더 받아 온 결과예요. 그래서 확신에 찬 말투가 정답의 신호가 되지 못해요.

## 5편 `v1-rag` — 자료를 붙여 주면 왜 덜 틀릴까? · RAG, 청크, 임베딩 검색

- 제목: 자료를 붙여 주면 왜 덜 틀릴까?
- 부제: RAG, 청크와 임베딩 검색
- summary: 규정 문서를 붙여 주면 AI가 덜 틀려요. 문서를 조각(청크)으로 자르고, 뜻을 숫자 좌표(임베딩)로 바꿔 질문과 가까운 조각을 찾아 함께 넣는 RAG의 원리와, 그래도 출처를 눌러 봐야 하는 이유를 담았어요.
- keywords: RAG, 검색 증강 생성, 청크, 임베딩, 벡터, 의미 검색, BM25, 인용, 근거, 출처 확인

핵심 주장: 4편의 할루시네이션은 기억(학습된 가중치)에 기대서 생겨요. RAG는 질문이 오면 먼저 자료에서 관련 조각을 찾아 질문과 함께 컨텍스트 창에 넣고, 모델은 그 조각을 보고 답하며 출처를 달아요. 검색은 문서를 청크로 자르고 각 청크를 임베딩(뜻을 나타내는 숫자 벡터)으로 바꿔, 질문 벡터와 가까운 청크를 고르는 방식이에요. 정확도는 "맞는 조각을 찾았느냐"에 달려서, 맥락이 잘린 청크는 검색에서 놓쳐요. 2026년에는 창이 커져 작은 자료는 통째로 넣기도 하고, 과거 대화 검색도 같은 원리로 돌아가요.

### 확인된 사실

1. RAG는 사전학습된 생성 모델(매개변수 기억)과 위키백과의 조밀 벡터 색인(비매개변수 기억)을 결합하고, 더 구체적이고 사실적인 글을 만들며 근거의 출처(provenance)를 제공해요. — Lewis 외, Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks, arXiv 2005.11401 (2020.5.22 제출, NeurIPS 2020) https://arxiv.org/abs/2005.11401
2. RAG는 할루시네이션, 오래된 지식, 추적할 수 없는 추론 과정 문제를 외부 데이터베이스로 보완해요. 나이브·어드밴스드·모듈러 RAG로 분류. — Gao 외, RAG for LLMs: A Survey, arXiv 2312.10997 (2023.12.18 제출, 2024.3.27 개정) https://arxiv.org/abs/2312.10997
3. RAG는 정확성과 근거를 높이지만, 효과는 외부 지식의 품질과 실행 시점에 검색된 내용의 관련성에 달려 있어요. — Claude 용어집(RAG) https://platform.claude.com/docs/en/about-claude/glossary
4. 청크로 자르면 맥락이 사라져 검색이 실패해요. 예: "회사 매출이 3% 늘었다"라는 청크에는 어느 회사·어느 시기인지가 없어요. 각 청크 앞에 50~100토큰의 설명 맥락을 붙이는 Contextual Retrieval로 상위 20개 청크 검색 실패율이 임베딩만 쓸 때 35%, BM25와 결합 시 49%(5.7%→2.9%), 재순위까지 더하면 67%(5.7%→1.9%) 줄었어요. 지식 베이스가 20만 토큰보다 작으면 전체를 프롬프트에 넣는 편이 간단하다고 안내해요. — Anthropic, Introducing Contextual Retrieval (2024-09-19) https://www.anthropic.com/news/contextual-retrieval
5. (2026 흐름) 임베딩은 텍스트·이미지 등을 하나의 임베딩 공간의 숫자 벡터로 바꾸고, 키워드 방식보다 맥락을 반영한 의미 검색·분류·군집에 쓰이며 RAG에서 사실 정확도를 높이는 핵심 역할을 해요. 기본 출력은 3072차원(128까지 줄일 수 있음). 최신 모델 `gemini-embedding-2`는 텍스트·이미지·영상·오디오·문서를 다루는 첫 멀티모달 임베딩 모델이라고 소개해요. — Gemini API Embeddings https://ai.google.dev/gemini-api/docs/embeddings (날짜 표기 없음 / 확인 2026-10-02)
6. Citations 기능은 각 주장을 뒷받침하는 원문 구절을 정확히 돌려줘서 답을 검증하고 출처를 보여 줄 수 있게 해요. 모든 활성 모델이 지원. — Claude 문서 Citations https://platform.claude.com/docs/en/build-with-claude/citations (확인 2026-10-02)
7. NotebookLM은 사용자의 노트와 자료에 언어 모델을 "그라운딩"하고, 여러 자료를 쓸 때 각 응답에 원문 인용을 붙여 사실 확인을 쉽게 해요. 소스 그라운딩이 할루시네이션을 줄이는 것으로 보이지만 사용자가 확인해야 한다고 밝혀요. — Google 블로그, Introducing NotebookLM (2023-07-12) https://blog.google/technology/ai/notebooklm-google-ai/
8. (2026 흐름) Claude의 채팅 검색은 요청할 때만 RAG로 과거 대화를 찾아오고, 도구 호출로 표시돼요. — Claude 고객지원 chat search and memory https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context

기존 e6에서 가져올 것: 장면 1(자료 없이 물으면), 장면 2(RAG 흐름), 장면 5(그래도 줄어들 뿐), 만져 보기 "같은 질문, 두 가지 답 비교"(예시 규정임을 밝히는 문구 유지). 버릴 것: 장면 4의 제품 소개 비중(제품명은 사례 한 줄로만).

### 장면 초안

1. 사례: 자료 없이 규정을 물으면 (13초) — e6 장면 1 재사용
   - 자막: "우리 학교 현장체험학습 규정에서 인솔 교사 비율이 어떻게 되죠?" / 자료 없이 물으면 AI는 그럴듯한 숫자를 지어낼 수 있어요. 4편에서 본 그 이유 때문이에요.
2. RAG의 흐름 (14초)
   - 자막: 그래서 쓰는 방법이 <em>RAG</em>, 검색 증강 생성이에요. 질문이 오면 먼저 자료에서 관련 조각을 찾아요. / 찾은 조각을 질문과 함께 책상(컨텍스트 창)에 올리면, 모델은 기억 대신 그 조각을 보고 답하고 출처를 달아요. 2020년 연구가 이 구조를 제안했어요.
   - 무대: 질문 → 검색 → 조각+질문 → 답+출처 4박스(e6 장면 2).
3. 조각 찾기: 청크와 임베딩 (14초)
   - 자막: 문서는 먼저 <em>청크</em>라는 문단 조각으로 잘려요. 각 조각은 뜻을 담은 숫자 좌표, <em>임베딩</em>으로 바뀌어요. / 질문도 좌표로 바꾸고, 가장 가까운 조각을 골라요. 단어가 똑같지 않아도 뜻이 비슷하면 가까워요.
   - 무대: 왼쪽 문서 → 칩 6개(청크) → 오른쪽 2D 평면에 점 6개, 질문 별표 점, 가장 가까운 점 2개에 원.
4. 조각이 맥락을 잃으면 (13초)
   - 자막: 그런데 "15명당 1명"이라는 조각만 떼어 놓으면, 어느 학교의 무슨 규정인지가 사라져요. 그래서 검색이 놓쳐요. / 2024년 한 실험은 조각마다 짧은 머리말을 붙여 검색 실패를 절반 가까이 줄였어요. 그리고 자료가 작으면 아예 통째로 넣는 편이 간단하다고 해요.
   - 무대: 청크 "15명당 1명" 회색 → 머리말 칩 "○○초 현장체험학습 규정 제3조" 붙으며 aqua로. 숫자 "실패 5.7% → 2.9%".
5. 그래도 줄어들 뿐: 출처를 눌러요 (13초) — e6 장면 5 변형
   - 자막: 찾은 자료가 틀렸거나 엉뚱한 조각을 찾으면 답도 틀려요. RAG는 실수를 줄일 뿐 없애지 않아요. / 2026년엔 지난 대화를 찾아 주는 기능도 같은 원리로 돌아가요. 그래서 답에 달린 인용을 눌러 원문과 한 번 대조하는 습관이 핵심이에요.
   - 무대: 오류 두 경우 박스 + "인용 [1] 눌러 원문 확인" 칩. 쿼카 point.

### 만져 보기 "규정 조각 찾기"

- 예시 규정 6조각(e6의 PARAGRAPHS 확장, "실제 규정이 아닌 예시예요" 유지). 각 조각에 고정 2D 좌표(임베딩을 흉내 낸 값). 질문 3개 중 선택 → 질문 좌표와의 거리로 상위 2조각을 결정적으로 골라 하이라이트, 그 조각만 넣은 "예시 답변 + [n] 인용" 표시. 인용 누르면 원문 조각 강조.
- 질문 하나("체험학습 몇 명당 선생님 한 명?")는 기본 상태에서 엉뚱한 조각(기타 조항)을 찾도록 좌표를 설정.
- primary 버튼 "조각에 머리말 붙이기": 각 조각 좌표가 결정적으로 이동해 그 질문이 맞는 조각을 찾게 됨(DOM 변화). 아래에 "머리말이 없을 때 / 있을 때" 비교 한 줄.

### teacherLines
- "AI에게 자료를 같이 주는 건 <b>교과서를 펴 놓고 시험 보는 것</b>과 같아요. 훨씬 덜 틀려요."
- "그래도 교과서가 틀렸으면 답도 틀려요. <b>인용을 눌러 원문을 확인</b>하는 게 우리 일이에요."

### tip
- body: 공문·규정처럼 짧은 자료는 통째로 붙이고, "답의 각 문장에 근거 조항을 [1]처럼 달아 줘"라고 요청하세요. 인용이 없는 숫자는 쓰지 않아요.
- extra: 여러 문서를 올릴 땐 파일 이름을 "2026_○○초_현장체험학습규정"처럼 학교·연도·주제가 드러나게 붙이세요. 조각이 맥락을 잃는 문제를 사람이 먼저 줄이는 방법이에요.

### myth
- myth: 자료를 붙여 주면 AI는 절대 틀리지 않는다.
- fact: 검색이 엉뚱한 조각을 찾거나 자료 자체가 틀리면 답도 틀려요. RAG는 실수를 줄이는 방법이고, 인용을 눌러 원문과 대조하는 확인은 여전히 필요해요.

## 6편 `v1-reasoning` — "생각하는 시간"이 있는 AI는 무엇이 다를까? · 추론 모델과 노력 수준 (살리는 편)

- 제목: "생각하는 시간"이 있는 AI는 무엇이 다를까?
- 부제: 추론 모델과 노력 수준(effort)

### 확인된 사실

1. 중간 추론 단계(생각의 사슬)를 생성하게 하면 복잡한 추론 능력이 크게 오르고, 5,400억 파라미터 모델에 생각의 사슬 예시 8개만 주어 GSM8K(수학 문장제)에서 최고 성능을 냈어요. — Wei 외, Chain-of-Thought Prompting Elicits Reasoning in LLMs, arXiv 2201.11903 (2022.1.28 제출) https://arxiv.org/abs/2201.11903
2. 사람이 만든 풀이 예시 없이 순수 강화학습만으로 추론 능력을 끌어낼 수 있고, 자기 성찰·검증 같은 추론 패턴이 생겨났어요. — DeepSeek-AI, DeepSeek-R1, arXiv 2501.12948 (2025.1.22 제출, Nature 645권 633–638쪽, 2025) https://arxiv.org/abs/2501.12948
3. 추론 시점 연산을 문제 난이도에 맞춰 배분하면 단순 방식보다 4배 이상 효율적이고, 연산을 더 쓴 작은 모델이 FLOPs가 같은 조건에서 14배 큰 모델과 맞먹거나 앞설 수 있어요. — Snell 외, Scaling LLM Test-Time Compute Optimally…, arXiv 2408.03314 (2024.8) https://arxiv.org/abs/2408.03314
4. o1류 추론 모델은 간단한 문제(2+3 같은)에도 지나치게 긴 사고를 쓰는 "과잉 사고(overthinking)"를 보이고, 정확도를 지키면서 이를 줄이는 방법을 제안해요. — Do NOT Think That Much for 2+3=? On the Overthinking of o1-Like LLMs, arXiv 2412.21187 (2024.12 제출, 2025.2 개정) https://arxiv.org/abs/2412.21187
5. 생각이 켜지면 Claude는 답하기 전에 질문을 다시 정리하고, 접근법을 시도하고, 중간 결과를 확인하고, 안 되는 길을 버려요. 그래서 수학·코딩·분석·긴 에이전트 작업에서 성능이 오르지만, 생각에 쓴 토큰은 생각 내용이 반환되지 않아도 출력 토큰으로 과금돼요. 생각 블록에 보이는 글은 "원래의 생각의 사슬이 아니라 요약"이에요. — Claude 문서 Thinking https://platform.claude.com/docs/en/build-with-claude/thinking (날짜 표기 없음 / 확인 2026-10-02)
6. (2026 흐름) 같은 문서의 모델별 표: Claude Opus 5.5·Sonnet 5.5 등 최신 모델은 thinking 필드를 안 보내도 적응형 사고(adaptive thinking)가 켜져 있고, Opus 5.5는 끌 수 없어요(disabled는 400 오류). — 같은 URL. 마이그레이션 가이드도 "적응형 사고는 항상 켜져 있고, 생각 깊이는 effort 파라미터로만 조절"이라고 밝혀요. — https://platform.claude.com/docs/en/models/opus-5-5/migration-guide
7. (2026 흐름) 노력 수준(effort)은 응답의 철저함과 토큰 효율을 맞바꾸는 손잡이예요. low·medium·high·xhigh·max 다섯 단계, Opus 5.5 기본은 medium, 다른 모델은 high. 낮은 수준에서는 쉬운 문제에서 생각을 아예 건너뛸 수 있고, 어려운 문제에서는 여전히 생각하되 덜 생각해요. 간단하거나 속도가 중요한 일엔 low를 쓰라고 권해요. Opus 4.7 안내에는 max가 일부 과제에서 과잉 사고로 이어질 수 있다는 문장이 있어요. — Claude 문서 Effort https://platform.claude.com/docs/en/build-with-claude/effort (확인 2026-10-02)
8. (2026 흐름) Gemini 3 계열도 생각 과정으로 추론·다단계 계획 능력을 높이고, 생각 수준(thinkingLevel: minimal·low·medium·high)을 고를 수 있어요. 생각이 켜지면 요금은 출력 토큰과 생각 토큰의 합이고, 사실 조회처럼 단순한 일엔 minimal이나 low를 쓰라고 안내해요. — Gemini API Thinking https://ai.google.dev/gemini-api/docs/thinking (확인 2026-10-02)
9. 추론 모델은 판단에 쓴 힌트를 생각 과정에서 항상 밝히지 않아요. 힌트를 사용했을 때 언급한 비율이 Claude 3.7 Sonnet 25%, DeepSeek R1 39%였어요. — Anthropic, Reasoning models don't always say what they think (2025-04-03) https://www.anthropic.com/research/reasoning-models-dont-say-think

## 7편 `v1-ai-label` — AI로 만든 건 어떻게 표시할까? · AI 기본법 제31조와 C2PA

핵심 주장: 표시는 두 겹이에요. 사람 눈에 보이는 표시(라벨·자막·설명란)와 기계가 읽는 표시(파일 안 서명된 출처 정보 C2PA, 픽셀·소리에 숨긴 워터마크). 한국 AI 기본법 제31조는 AI사업자에게 ① 사전 고지 ② 생성형 AI 결과물 표시 ③ 실제와 구분하기 어려운 결과물(딥페이크)은 이용자가 명확히 인식하도록 고지·표시를 요구해요. 정부는 딥페이크가 아닌 결과물에는 비가시 워터마크도 허용했고, 과태료는 최소 1년 이상 계도기간을 둬요. 학교가 영상을 올리는 플랫폼(YouTube)은 사실적인 합성 콘텐츠 공개를 자체 정책으로 요구하고 C2PA 정보를 읽어 라벨을 붙여요. C2PA는 "이 파일이 어디서 어떻게 만들어지고 고쳐졌는지"를 위조 방지 서명으로 담을 뿐, 내용이 참인지 판정하지는 않아요.

### 장면 초안

1. 이름이랑 성적, 넣어도 되나? (13초) — s4 장면 1 재사용

2. 내가 넣은 글은 어디로 가나 (14초) — s4 장면 2 개편
   - 자막: 채팅창에 넣은 글은 서비스 서버로 가요. 한 서비스는 학습에 쓰도록 허용하면 5년, 아니면 30일 보관해요. / 다른 서비스는 일부 대화를 사람이 검토하고, 검토된 대화는 최대 3년 보관한다며 "기밀 정보는 넣지 말라"고 직접 안내해요. 설정 화면의 <em>학습 사용</em>과 <em>활동 저장</em>을 꼭 확인해요.
   - 무대: 채팅창 → 서버 상자 → 칩 3개(저장 기간 / 사람 검토 / 학습 사용). 
3. 학생 정보는 개인정보, 그리고 2025년 12월 기준 (14초)
   - 자막: 이름·사진·학번·성적·건강·가정 사정은 개인정보예요. 개인정보보호위원회는 2025년에 생성형 AI 개인정보 처리 안내서를 냈어요. / 2025년 12월 교육부와 교육청의 수행평가 AI 관리 방안도 다섯 영역 중 하나로 <em>개인정보 보호</em>를 넣고, 개인정보 입력에 각별히 주의하라고 했어요.
   - 무대: 개인정보 칩 6개(s4 장면 3) + 아래 "수행평가 AI 관리 방안 5영역" 카드(범위 설정 / 과정 표기 / 사전교육 / 평가 설계 / 개인정보 보호, 마지막만 오렌지).
4. 수행평가와 기록: AI는 금지가 아니라 규칙이 먼저 (14초)
   - 자막: 관리 방안은 AI를 일률적으로 막지 않아요. 대신 평가 전에 허용 범위와 금지 행위를 미리 알리고, 학생이 쓴 AI 종류와 프롬프트를 <em>출처로 밝히게</em> 해요. / 그리고 결과물만 받지 않고, 수업 시간에 과정을 직접 보는 평가로 바꿔요. 학생에 대한 기록도 마찬가지로, 교사가 직접 본 것이 바탕이에요.
   - 무대: 공지문 카드("AI로 생성한 글이나 이미지 출처를 밝히지 않고 창작물로서 제출하는 행위는 부정행위") + 출처 표기 예시 칩("사용한 AI · 프롬프트") + "수업 중 과정 관찰" 상자.
   - (기재요령 AI 조항 원문이 확인되면 두 번째 자막을 그 원문 요지로 교체)
5. 넣기 전 3초 점검 (13초) — s4 장면 5 재사용
   - 자막: 넣기 전에 3초만 점검해요. 이름? 사진? 건강 같은 민감정보? 이름은 학생A로, 학번은 지우고, 사진은 얼굴을 가려요. / 학교가 승인한 도구인지, 학습 사용 설정이 꺼져 있는지 보고, 학생에게도 말해 줘요. "네 이름과 사진은 AI에 넣지 않아."

### 만져 보기 "프롬프트 가리기 시뮬레이터" (s4 재사용 + 보강)

### tip
- body: 학생 관련 문구를 AI로 다듬을 땐 이름은 학생A, 학번 삭제, 건강·가정 정보는 빼고, 교사가 직접 관찰한 사실만 짧게 넣으세요. 결과 문장은 내가 본 사실과 맞는지 한 줄씩 대조한 뒤 내 문장으로 고쳐 써요.
- extra: 수행평가 공지문에는 허용 범위(아이디어 찾기만 허용 등)와 금지 행위, 출처 적는 칸(사용한 AI·프롬프트)을 함께 넣어 두면 학생도 교사도 헷갈리지 않아요.
