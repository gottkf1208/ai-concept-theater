## 9편 `v2-seed` — 같은 프롬프트인데 왜 다른 영상이 나올까?

- 부제: 시드와 확산 모델
- summary: 같은 프롬프트를 두 번 넣었는데 영상이 다르게 나온 이유를 "첫 잡음"으로 풀어요. 시드가 첫 잡음을 정하는 번호라는 것, 시드를 고정해도 완전히 같지는 않은 이유, 그래서 무엇을 기록해야 하는지까지.
- keywords: 시드, 초기 잡음, 확산 모델, 흐름 매칭, 재현성, 결정성, 샘플링
- 참고 편: `episodes/e2-seed.js`(장면 1·2·4·5 골격 재사용). 단, e2의 "다음 단어 확률·온도" 장면은 1편(v1-next-token)과 겹치니 빼고, 이미지·영상 쪽에 집중해요.
- 고칠 것: e2 장면 4의 "시드 항목이 아예 없는 도구도 있고" 같은 범위 흐리기 → "시드를 화면에 안 보여 줘도 내부에서는 매번 새 시드로 첫 잡음을 만들어요"로 메커니즘을 말해요.

핵심 주장: 이미지·영상 모델은 무작위 잡음(초기 잡음 텐서)에서 출발해 여러 단계에 걸쳐 잡음을 걷어 내요. 시드는 그 첫 잡음을 만드는 난수 발생기의 시작 번호예요. 시드가 다르면 출발점이 달라서 같은 프롬프트라도 다른 그림이 나와요. 2024년 이후 주류가 된 흐름 매칭(정류 흐름) 방식도 출발점은 잡음이라 원리는 같아요. 시드를 고정해도 하드웨어·소프트웨어 버전·계산 순서 차이로 결과가 완전히 같다는 보장은 없어요. 공식 영상 API 문서도 시드는 "결정성을 보장하지 않고 약간 높여 줄 뿐"이라고 적어요.

### 확인된 사실
1. 확산 모델의 기본 논문: Ho·Jain·Abbeel, "Denoising Diffusion Probabilistic Models", arXiv 2006.11239, 2020-06-19 제출. https://arxiv.org/abs/2006.11239 (확인 2026-10-02)
2. 흐름 매칭: "Flow Matching for Generative Modeling", arXiv 2210.02747, 2022-10-06 제출. 최적 수송(OT) 경로가 확산 경로보다 효율적이고 학습·샘플링이 빠르다고 밝힘. https://arxiv.org/abs/2210.02747 (확인 2026-10-02)
3. 2024년 SD3 논문 초록: 확산 모델은 데이터를 잡음 쪽으로 보내는 경로를 거꾸로 돌려 잡음에서 데이터를 만들고, 정류 흐름(rectified flow)은 데이터와 잡음을 직선으로 잇는 방식. arXiv 2403.03206, 2024-03-05 제출. https://arxiv.org/abs/2403.03206 (확인 2026-10-02)
4. Hugging Face Diffusers 공식 문서: 파이프라인은 `torch.randn`으로 **첫 잡음 텐서**를 만들고, 같은 결과를 원하면 Generator에 시드를 줘야 함. 재현성이 중요하면 CPU Generator 권장(GPU와 CPU의 난수 발생기가 다름). Generator는 쓰면 상태가 바뀌어 같은 객체로 다시 부르면 다른 결과. 결정적 알고리즘을 켜도 "같은 시드로도 보장되지는 않는다". https://huggingface.co/docs/diffusers/using-diffusers/reusing_seeds (확인 2026-10-02)
5. PyTorch 공식 문서(Reproducibility): "PyTorch 릴리스, 개별 커밋, 플랫폼이 다르면 완전한 재현은 보장되지 않고, 같은 시드라도 CPU와 GPU 실행 결과가 다를 수 있다." https://docs.pytorch.org/docs/2.14/notes/randomness.html (확인 2026-10-02)
6. Gemini API Veo 3.1 공식 문서: seed는 Veo 3 계열에서 쓸 수 있고 "결정성을 보장하지 않지만 약간 높여 준다". 문서 갱신 2026년 1월(Veo 3.1)·3월(Lite). https://ai.google.dev/gemini-api/docs/veo (확인 2026-10-02)
7. (1편과 연결용) Claude 용어집: 온도 0이어도 완전히 결정적이지 않고 같은 입력이 다른 출력을 낼 수 있음. https://platform.claude.com/docs/en/about-claude/glossary (확인 2026-10-02)

### myth
- myth: 시드만 같으면 언제 어디서나 똑같은 그림이 나온다.

## 10편 `v2-text-render` — 글자와 손가락은 왜 뭉개질까?

- 부제: 확산 모델과 텍스트 렌더링 학습
- summary: 영상 제목의 TEMPERATURE가 뭉개진 이유와, 요즘 모델의 글자가 왜 좋아졌는지를 풀어요. 텍스트 인코더가 글자를 "덩어리"로 봤던 문제, 글자를 보는 인코더·합성 글자 데이터·작은 글자를 살리는 디코더까지. 한글이 아직 더 어려운 이유도요.
- keywords: 텍스트 렌더링, 확산 모델, 텍스트 인코더, 문자 인식(character-aware), 토큰, 합성 데이터, 커리큘럼 학습, VAE 디코더, 한글 음절
- 참고 편: `episodes/e3-diffusion.js`(장면 1 사례 이미지 `assets/frames/v1-07s.webp`, `v1-07s-title.webp`와 장면 2 잡음 데모 재사용).
- 고칠 것: e3 장면 5 자막 "안 통하는 도구도 있고요" 삭제. "'no text'라고 적어 보기"는 근거를 확인 못 했으니(아래 확인 불가) 메커니즘이 확인된 팁(정확한 글자는 편집 단계, 생성 후 확대 확인)으로 바꿔요.

핵심 주장: 확산 모델은 잡음을 걷어 내며 "대략 그럴듯한" 패턴을 그리는 데 강해요. 나무·구름은 조금 틀려도 티가 안 나지만 손가락(개수·관절, 변형과 가림이 많음)과 글자(정확한 획·철자)는 조금만 어긋나도 티가 나요. 글자가 특히 약했던 큰 이유는 **텍스트 인코더가 낱글자를 못 봤기 때문**이에요. 프롬프트를 토큰 덩어리로 받아서 "그 단어가 어떤 글자들로 이루어졌는지"를 몰랐어요(2022년 연구: character-blind). 그 뒤 ① 글자 단위를 보는 인코더·더 큰 언어 모델 인코더, ② 그림 토큰과 글 토큰이 양방향으로 섞이는 구조, ③ 글자 그림을 일부러 만들어 쉬운 것부터 가르치는 학습, ④ 작은 글자를 살리도록 다듬은 디코더로 크게 좋아졌어요. 한글은 조합 가능한 음절이 11,172자이고, 2026년 다국어 평가에서도 글자 그리기에서 한국어가 뒤처졌어요.

### 확인된 사실
1. 손가락이 어려운 이유: 2023년 HandRefiner 초록 — 확산 모델은 "손가락 개수가 틀리거나 모양이 불규칙한" 손을 자주 만들고, 그 원인은 학습 이미지에서 손의 물리 구조와 자세를 배우는 일이 변형·가림이 많아 복잡하기 때문. arXiv 2311.17957, 2023-11-29 제출. https://arxiv.org/abs/2311.17957 (확인 2026-10-02)
2. 2022년 연구(Liu 외, "Character-Aware Models Improve Visual Text Rendering"): 널리 쓰인 텍스트-이미지 모델은 글자 단위 입력 특징이 없어(character-blind) 단어의 글자 구성을 예측하기 어렵고, 글자를 보는(character-aware) 인코더를 쓰면 희귀 단어 철자 정확도가 30점 이상 올랐음. arXiv 2212.10562, 2022-12-20 제출. https://arxiv.org/abs/2212.10562 (확인 2026-10-02)
3. 2022년 Imagen 초록: 언어 모델(텍스트 인코더) 크기를 키우는 것이 이미지 확산 모델 크기를 키우는 것보다 품질과 글-그림 일치를 훨씬 많이 올림. arXiv 2205.11487, 2022-05-23 제출. https://arxiv.org/abs/2205.11487 (확인 2026-10-02)
4. 2024년 SD3 논문: 그림과 글에 별도 가중치를 두고 그림 토큰과 글 토큰 사이에 정보가 양방향으로 흐르게 해 글 이해·타이포그래피·선호도가 좋아짐(초록). 본문: T5 인코더를 빼면 미감은 그대로(승률 50%)인데 글자 생성 능력 평가에서 승률 38%로 떨어짐. 잠재 채널 수를 늘리면 복원 성능이 크게 좋아짐. arXiv 2403.03206, 2024-03-05 제출. https://arxiv.org/abs/2403.03206 , https://arxiv.org/html/2403.03206 (확인 2026-10-02)
5. 2025년 Qwen-Image 기술 보고서: 복잡한 글자 그리기를 위해 수집·필터·주석·**합성**·균형 단계의 데이터 파이프라인을 만들고, 글자 없는 그림 → 쉬운 글자 → 문단 수준으로 넓혀 가는 **커리큘럼 학습**을 씀. 합성 전략은 단순 배경에 글자만 그리기 → 실제 장면에 글자 넣기 → 구조화된 템플릿 순. "작은 글자와 세부 복원을 위해 글자가 많은 이미지로 디코더를 학습"했고 "디코더만 미세조정해도 작은 글자 표현이 좋아진다". 글 입력 인코더로 Qwen2.5-VL(다국어 시각-언어 모델)을 씀. 영어 같은 알파벳 언어뿐 아니라 중국어에서도 큰 진전. arXiv 2508.02324, 2025-08-04 제출. https://arxiv.org/abs/2508.02324 , https://arxiv.org/html/2508.02324 (확인 2026-10-02)
6. 2024년 Glyph-ByT5-v2: 다국어 글리프-텍스트 쌍 100만 개 이상, 그래픽 디자인 이미지-텍스트 쌍 1,000만 개로 10개 언어 글자 그리기 지원. arXiv 2406.10208, 2024-06-14 제출. https://arxiv.org/abs/2406.10208 (확인 2026-10-02)
7. 한글 음절 수: 유니코드 FAQ — 미리 조합된 한글 음절 11,172자는 초성 19 × 중성 21 조합 399자 + 초성 19 × 중성 21 × 종성 27 조합 10,773자. https://www.unicode.org/faq/korean.html (확인 2026-10-02)
8. 2026년 다국어 평가(LingT2I, 10개 언어 3.3만 프롬프트, 한국어 포함): 글자 그리기 과제에서 "아랍어, 힌디어, 한국어가 크게 뒤처진다". 다국어 기반으로 처음부터 설계한 구조가 나중에 덧붙인 방식보다 언어 간 공정성에 더 효과적이라고 결론. arXiv 2608.11002, 2026-08-11 제출. https://arxiv.org/abs/2608.11002v1 , https://arxiv.org/html/2608.11002v1 (확인 2026-10-02)
9. 2026년 글자 편집 평가(MULTITEXTEDIT, 12개 언어): 평가한 12개 시스템 모두 영어 밖 언어에서 품질이 떨어졌고, 떨어짐은 큰 구도가 아니라 글자 정확도·문자 모양에 몰려 있었음. arXiv 2605.08163, 2026-05-04 제출. https://arxiv.org/abs/2605.08163 (확인 2026-10-02)

### tip
- body: 포스터·안내문처럼 틀리면 안 되는 글자는 그림을 만든 뒤 <b>편집 단계에서 텍스트로</b> 넣어요. AI가 그린 글자는 확대해서 획 하나까지 확인해요.

## 12편 `v2-consistency` — 캐릭터 얼굴은 왜 장면마다 바뀔까? (살리는 편)

- 부제: 일관성과 레퍼런스 이미지

3. FLUX.1 Kontext(2025): 여러 차례 편집에서 물체·인물 보존이 좋아져 반복 작업에 강하다(multi-turn consistency). arXiv 2506.15742, 2025-06-17 제출. https://arxiv.org/abs/2506.15742 (확인 2026-10-02)

## 14편 `v2-video-cost` — 영상은 왜 이미지보다 훨씬 비쌀까?

- 부제: 프레임 × 해상도 × 단계, 그리고 VAE 압축
- summary: 이미지 한 장보다 영상 몇 초가 훨씬 많은 크레딧을 쓰는 이유를, 프레임 수·해상도·단계 수와 VAE 압축으로 계산해 봐요. 영상 길이와 해상도에 왜 상한이 있는지, 공식 문서 숫자로 확인해요.
- keywords: 연산량, 크레딧, 프레임, 잠재 공간, VAE, 토큰, 어텐션, 시공간 압축, 단계 수, 해상도 상한
- 참고 편: `episodes/next/n2-video-cost.js`(장면 1·2·3 골격, 만져 보기 "연산량 비교기" 골격).
- 고칠 것(**사실 오류**)
  - n2 만져 보기 체크박스 "켜면 1/8 배수로 줄어들어요" → 틀렸어요. VAE는 **가로·세로를 각각 1/8**로 줄이니 면적(픽셀 칸 수)은 **1/64**, 영상 VAE는 시간도 **1/4**로 줄여요(사실 2·3). 대신 채널 수가 늘어요(3 → 4 또는 16).
  - n2 myth fact "잠재 공간 압축을 써도 프레임 수만큼은 줄지 않아요" → 영상 VAE는 시간 축도 4배 압축하니 "프레임 수에 비례해 늘어나는 건 그대로"로 고쳐요.
  - n2 script "수십 배 이상"은 근거 없는 수치 → 아래 계산값으로 바꾸거나 "훨씬"으로.

핵심 주장: 영상은 초당 수십 장(공식 문서 예: 24fps, 8초면 192장)이고, 시간 축까지 함께 계산해요. 그대로는 너무 커서 VAE로 압축한 잠재 공간에서 계산해요(가로·세로 1/8, 영상은 시간 1/4). 그래도 영상 하나를 조각(토큰)으로 자르면 이미지 한 장보다 토큰이 훨씬 많고, 트랜스포머의 어텐션 계산은 **토큰 수의 제곱**으로 늘어요. 거기에 잡음 걷기 단계마다 이 계산을 반복해요. 그래서 비싸고, 그래서 공식 문서에도 고해상도는 짧은 길이로만 열려 있고, 길게는 짧은 조각을 이어 붙여요. 압축을 더 세게 하면 싸지지만 세부가 사라지는 맞바꿈이 있어요.

### 계산값 (확인된 사양으로 직접 계산, 화면에는 "계산해 보면" 표기)
- 이미지 1장 1024×1024, VAE 1/8 + 조각 2×2 → 64×64 = **4,096 토큰**.
- 영상 1280×720, 81프레임(Wan 사양) → 잠재 [1+80/4=21, 90, 160] → 조각 (1,2,2) → 21×45×80 = **75,600 토큰**(이미지의 약 18.5배).
- 어텐션은 토큰 수의 제곱 → 18.5² ≈ **약 340배**(선형 층은 약 18.5배). 이 계산을 잡음 걷기 단계 수만큼 반복.
- 압축 효과: 원본 81×720×1280×3 ≈ 2억 2,395만 값 → 잠재 21×90×160×16 ≈ 484만 값(약 1/46).
- 24fps × 8초 = 192프레임(사실 7 사양).

### 확인 불가
- 상용 서비스의 크레딧 단가와 실제 연산량의 비례 관계: 공식 근거 없음 → "크레딧 = 연산량"이라고 단정하지 말고 "연산량이 크니 크레딧도 크게 매겨요" 정도로.
- 상용 모델(Veo·Kling·Seedance)의 VAE 압축비·단계 수: 공개 안 됨 → 압축비 수치는 공개 모델(SD, Wan, LTX-Video) 것만.

### 장면 5개 초안 (합계 약 66초)
1. **크레딧 창을 보고 놀랐어요** (13초): n2 장면 1 그대로(막대 둘). 자막 3: "답은 <em>프레임 수 × 해상도 × 단계 수</em>예요."
2. **8초면 그림 192장** (13초): 필름 띠(n2 장면 2) + 숫자 "24장/초 × 8초 = 192장". 자막: "공식 문서 기준으로 영상은 1초에 24장, 8초면 <em>192장</em>이에요." / "게다가 앞뒤 장면이 자연스럽게 이어지도록 <em>시간 축</em>까지 함께 계산해요."
3. **압축해서 계산해요: VAE** (14초): 원본 칸(큰 격자) → VAE → 잠재 칸(가로·세로 1/8, 영상은 시간도 1/4). 자막: "그대로는 너무 커서 <em>VAE</em>라는 압축기로 줄인 뒤 계산해요. 가로·세로를 각각 8분의 1로, 그러니 넓이는 <em>64분의 1</em>이에요." / "영상은 시간도 4분의 1로 줄여요. 압축을 더 세게 하면 더 싸지만, 2024년 연구는 <em>세부가 사라지는</em> 대가가 있다고 했어요."
4. **토큰의 제곱, 그리고 단계마다 반복** (14초): 칩 "이미지 4,096 토큰" vs "영상 75,600 토큰"(계산값), 아래 정사각형 두 개(한 변이 18.5배인 넓이 비교 = 제곱 시각화). 자막: "압축해도 영상은 조각이 훨씬 많아요. 계산해 보면 1024 이미지가 약 4천 조각, 720p 81프레임 영상은 약 7만 6천 조각이에요." / "조각끼리 서로 비교하는 <em>어텐션</em>은 조각 수의 <em>제곱</em>으로 늘고, 잡음 걷기 단계마다 반복돼요." / "그래서 한 공식 영상 API는 1080p·4K를 <em>8초 길이로만</em> 열어 둬요."
5. **초안은 작게, 최종만 크게** (12초): 단계 3칸(360p·짧게 여러 번 → 고르기 → 최종만 키우기/잇기). 자막: "2026년 영상 모델 공식 안내도 <em>360p는 초안용</em>, 고른 것만 크게 키우라고 해요." / "긴 영상은 한 번에가 아니라 <em>짧은 조각을 이어</em> 만들어요. 길이·해상도 상한은 계산량과 메모리의 한계예요."

### 만져 보기 "연산량 계산기" (결정적, n2 골격 개편)
- range: 해상도(360p/480p/720p/1080p, 16:9), 길이(1~8초), fps(12/24), 단계 수(4/8/20/50).
- 체크(초기 해제) "VAE로 압축(가로·세로 1/8, 시간 1/4)", "조각 2×2로 묶기".
- 출력 세 줄: ① 픽셀 칸 수(프레임×가로×세로) ② 토큰 수(압축·조각 반영: `(1+floor((frames-1)/4)) × ceil(H/16) × ceil(W/16)`, 압축을 끈 상태는 `frames × H × W`를 그대로 토큰으로 가정) ③ 상대 계산량 = 토큰² × 단계 수, 기준은 1024×1024 이미지 1장·같은 단계 수 = 1배. 막대는 로그 스케일.

### tip
- body: 영상은 <b>360p·짧게</b> 여러 번 만들어 보고, 마음에 드는 것 하나만 고화질로 키우거나 이어 붙여요. 크레딧을 가장 많이 아끼는 순서예요.
- extra: 한 공식 영상 API는 1080p·4K를 8초 길이로만 열어 두고, 더 길게는 7초씩 이어 붙이게 해요. 긴 영상이 필요하면 8초 안팎 조각을 여러 개 만들어 편집 프로그램에서 이어요(29편 긴 영상과 연결).

### myth
- myth: 영상도 이미지 생성기를 프레임 수만큼 돌리는 것뿐이다.
- fact: 영상은 프레임 사이 시간 관계까지 함께 계산해요. 조각 수가 많아지면 어텐션 계산은 그 <b>제곱</b>으로 늘고, 잡음 걷기 단계마다 반복돼요. 압축(VAE)으로 줄여도 이미지보다 훨씬 커요.

## 15편 `v2-voice` — 목소리는 어떻게 만들어질까?

- 부제: TTS·음성 복제·동의
- summary: 자막 프로그램이 붙여 준 AI 목소리가 사람 목소리랑 구분이 안 됐어요. 글자가 소리가 되는 과정, 몇 초 녹음으로 목소리를 흉내 내는 원리, 그리고 2026년에 바뀐 표시·동의 규칙까지.
- keywords: TTS, 음성 합성, 음성 복제, 제로샷, 운율, 동의, 법정대리인, 생체정보, AI 기본법, EU AI법 제50조, 워터마크
- 참고 편: `episodes/s3/s3-voice.js`(장면 1·2 골격).
- 고칠 것
  - s3 장면 3 자막 3 "서비스에 따라 <em>가능 여부와 품질</em>이 달라요." 삭제 → 메커니즘으로 교체(아래 장면 3).
  - s3 sources의 개인정보위 첫 화면 링크 → 조문·보도자료 원문 링크로.
  - s3 만져 보기의 브라우저 낭독(Web Speech)은 기기마다 목소리 목록이 달라 결과가 결정적이지 않아요. v2는 결정적 판정기로 바꾸고, 낭독 기능은 쓰더라도 보조 버튼으로만.

핵심 주장: TTS는 글자를 발음 단위(음소)와 억양·길이(운율)로 바꾼 뒤 신경망이 소리를 새로 만들어요. 2023년 연구는 6만 시간 영어 음성으로 배운 모델이 **3초 녹음**만으로 처음 듣는 사람의 목소리를 흉내 냈어요. 2026년 영상 모델은 목소리 참고까지 받기 시작했고, 한 대형 모델은 사람의 말을 바꾸는 기능을 일부러 막아 뒀어요. 목소리는 개인정보이고 생체정보 범주에 들어가요. 학생(만 14세 미만)의 목소리를 쓰려면 법정대리인 동의가 필요해요. 2026년에는 표시 규칙이 실제로 시행됐어요. 한국 AI 기본법은 생성형 AI 결과물 표시를, EU AI법 제50조는 2026년 8월 2일부터 딥페이크(음성 포함) 고지와 기계가 읽을 수 있는 표시를 요구해요. 미국은 목소리·얼굴 복제 연방 법안이 상원 위원회를 통과한 단계예요.

## 16편 `v2-subtitle` — 자막은 왜 가끔 엉뚱할까?

- 부제: 음성 인식, 커스텀 보캐뷸러리, 번역 파이프라인
- summary: 자동 자막에서 "사회 시간"이 "사회시장"으로, 친구 이름이 엉뚱한 낱말로 나온 이유를 풀어요. 단어장(커스텀 보캐뷸러리)이 인식을 끌어당기는 원리와 너무 세게 당기면 생기는 일, 인식 뒤에 번역이 붙을 때 오류가 어떻게 번지는지까지.
- keywords: 자막, 음성 인식, STT, Whisper, 커스텀 보캐뷸러리, 컨텍스트 바이어싱, 가산점(boost), 번역 파이프라인, 캐스케이드, 고유명사
- 참고 편: `episodes/s3/s3-subtitle.js`(장면 1·2·3·4 골격, 만져 보기 "오인식 자막 고치기").
- 고칠 것
  - s3 장면 3 자막 3 "잡음, 겹치는 말, 사투리도" → "잡음, 겹치는 말, 지역 억양도"(주제 낱말로만, 어미 아님). 카드 라벨도 "지역 억양".
  - s3 장면 5 칩 "Web Speech API(크롬·엣지·사파리 지원)": 지원 범위를 1차 출처로 확인 못 함 → 삭제하고 "브라우저에도 음성 인식 기능이 있어요"로.
  - s3 tip extra "인식률이 올라가요" → 단정 대신 원리(후보 점수에 가산점)와 부작용(안 한 말이 끼어듦)까지 같이.

핵심 주장: 음성 인식은 소리 조각마다 특징을 뽑고 문맥과 함께 "가장 그럴듯한 글자"를 확률로 골라요(2022년 연구: 68만 시간 다국어 음성). 처음 듣는 이름은 아는 낱말로 바꿔 써요. **커스텀 보캐뷸러리(단어장)**는 미리 등록한 낱말 후보에 가산점(boost)을 줘서 그 낱말을 더 자주 고르게 하는 컨텍스트 바이어싱이에요. 가산점이 너무 크면 말하지 않은 낱말이 자막에 끼어드는 오인식(거짓 양성)이 늘어요(공식 문서 경고). 번역 자막은 보통 인식 → 번역 두 단계(캐스케이드)라 앞 단계 오타가 그대로 번역되고, 한 번에 하는 통합 모델은 2023년 연구에서 캐스케이드보다 조금 나았어요. 인식 뒤에 언어 모델로 교정하는 단계는 그럴듯한 과잉 교정을 만들 수 있어요(2026년 연구).

### 확인된 사실
1. Whisper(2022): 68만 시간의 다국어·다과제 지도 데이터로 키우면 미세조정 없이도 표준 벤치마크에서 잘 일반화. arXiv 2212.04356, 2022-12-06 제출. https://arxiv.org/abs/2212.04356 (확인 2026-10-02)
2. OpenAI 음성-텍스트 공식 문서: whisper-1은 지시를 따르는 일반 언어 모델이 아니고 **최대 224토큰**의 프롬프트를 받으며, 프롬프트로 제품명·약어·드문 낱말 인식을 도울 수 있음(토큰 한도 때문에 확장성은 제한). 번역 엔드포인트는 "영어로만" 번역. https://developers.openai.com/api/docs/guides/speech-to-text (확인 2026-10-02)
3. Google Cloud Speech-to-Text 공식 문서(모델 적응): 구문 집합(phrase set)은 특정 낱말·구문이 인식될 확률을 높이고, 여러 낱말 구문을 주면 그 순서로 인식될 가능성과 개별 낱말 인식 가능성도 높아짐. boost 값은 0보다 큰 실수, **실용 상한 20**. 값이 높으면 놓침(거짓 음성)은 줄지만 "오디오에 없던 낱말이 전사에 나타나는" **거짓 양성**이 늘 수 있으니 값을 오르내리며 실험하라고 권고. https://docs.cloud.google.com/speech-to-text/docs/adaptation-model (확인 2026-10-02)
4. Amazon Transcribe 공식 문서(커스텀 보캐뷸러리): 브랜드명·약어·**고유명사**처럼 잘 안 잡히는 낱말의 정확도를 높이는 용도. 계정당 100개 파일, 파일당 50KB, 항목당 256자. "커스텀 보캐뷸러리에 기밀 정보, **개인정보(PII)**, 건강 정보를 넣지 말라." https://docs.aws.amazon.com/transcribe/latest/dg/custom-vocabulary.html (확인 2026-10-02)

6. Deep Context(2018): 종단간 음성 인식에 추론 시 문맥 구문(학습 때 못 본 낱말 포함)을 넣는 CLAS, 기존 방식보다 최대 68% 상대 오류율 개선. arXiv 1808.02480, 2018-08-07 제출. https://arxiv.org/abs/1808.02480 (확인 2026-10-02)
7. 2026년 LOGIC: 음성 언어 모델에서 개체(이름 등) 인식은 여전히 어려운 과제. 기존 프롬프트 방식은 디코딩 때 가산점 세기를 명시적으로 조절할 수 없고, 생성형 오류 교정은 **환각성 과잉 교정**을 만들 수 있음. 11개 로캘에서 개체 오류율 평균 9% 상대 감소, 오경보 0.3% 증가. arXiv 2601.15397, 2026-01-21 제출. https://arxiv.org/abs/2601.15397 (확인 2026-10-02)

9. SeamlessM4T(2023): 최대 100개 언어 음성 인식·번역 단일 모델. 기존 음성 번역은 단계를 차례로 잇는 캐스케이드 방식. 강한 캐스케이드 대비 영어로의 음성→텍스트 번역 BLEU 1.3점 향상. arXiv 2308.11596, 2023-08-22 제출. https://arxiv.org/abs/2308.11596 (확인 2026-10-02)

### 장면 5개 초안 (합계 약 67초)
1. **자막이 이상해요** (13초): s3 장면 1 그대로.
2. **소리를 글자로 추정해요** (13초): s3 장면 2 그대로(파형 → 특징 → 확률 → 후보 "사회 시간"/"사회시장", 2022년 연구 68만 시간).
3. **단어장은 후보에 가산점을 줘요** (14초): 후보 막대 3개("한소라" 0.46 / "한소리" 0.41 / "한솔이" 0.13, 예시 값 표기) → 단어장에 "한소리" 등록 → "한소리" 막대가 올라가 1등. 다음에 다른 줄 "오늘 발표는 한 소리로 맞춰요"(말한 건 '한 소리')에서 가산점을 크게 주면 "한소리"로 바뀌는 오인식. 자막: "<em>커스텀 보캐뷸러리</em>, 단어장에 이름을 넣으면 그 낱말 후보에 <em>가산점</em>이 붙어요." / "그런데 가산점을 너무 크게 주면 말하지 않은 낱말까지 끼어들어요. 공식 문서도 이걸 경고해요."
4. **번역은 한 단계 더** (13초): s3 장면 4 골격(음성 → 자막 → 번역). 자막: "번역 자막은 보통 인식 다음에 번역을 <em>따로</em> 붙여요. 그래서 앞 단계 오타가 그대로 번역돼요." / "2023년 연구에서는 한 번에 하는 모델이 조금 나았고, 2026년 연구는 언어 모델로 고치는 단계가 <em>그럴듯하게 틀린 교정</em>을 만들 수 있다고 했어요."
5. **이렇게 확인해요** (14초): 박스 3개 ① 고유명사 → 숫자 → 동음이의어 순서로 검수 ② 단어장은 꼭 필요한 낱말만, 가산점은 작게부터 ③ 학생 이름을 클라우드 단어장에 넣는 건 개인정보라 조심. 자막: "한 클라우드 공식 문서는 단어장에 <em>개인정보를 넣지 말라</em>고 적어요. 학생 실명은 성 빼고 이름만, 또는 검수 때 고치기로 해요." / "교실에 트는 안내 자막은 <em>사람이 한 번</em> 읽어 보고 내보내요."

### 만져 보기 "단어장 가산점 다이얼" (결정적)
- 자동 자막 4줄(코드 상수). 각 줄은 문제 낱말 자리의 후보 목록과 기본 점수를 가짐. 예:
  - 줄1 실제 발화 "한소리 학생" — 후보 한소라 0.46 / 한소리 0.41 / 한솔이 0.13
  - 줄2 실제 발화 "사회 시간" — 사회시장 0.52 / 사회 시간 0.48
  - 줄3 실제 발화 "한 소리로 맞춰요" — 한 소리 0.62 / 한소리 0.30 / 한소라 0.08 (단어장 낱말이 실제로 없는 줄)
  - 줄4 실제 발화 "미술 시간" — 미술 0.70 / 미슬 0.30
- `button.primary` "단어장에 등록"(한소리, 사회 시간): 등록 낱말 칩 표시 + 아래 range 활성화(DOM 변화).
- range "가산점" 0~20: 등록 낱말 후보 점수에 `boost × 0.02`를 더해 다시 정렬 → 1등 후보가 자막에 표시. 결정적 결과: 0~4는 변화 없음, 5~12는 줄1·줄2가 바로잡힘(초록 테두리), 15 이상은 줄3에 거짓 양성 "한소리"가 끼어듦(주황 테두리, "안 한 말이 들어갔어요"). range 최대값 20에서 DOM 변화 보장.
- 상태 문장: "가산점 8: 이름이 맞게 나와요." / "가산점 18: 다른 줄에 안 한 말이 끼어들었어요. 공식 문서도 이걸 경고해요."
- 보조 버튼 "정답 보기": 실제 발화 표시.

### teacherLines
- "자막 AI는 소리를 듣고 <b>가장 그럴듯한 글자</b>를 골라요. 그래서 처음 듣는 이름은 잘 틀려요."
- "단어장에 이름을 넣으면 그 이름이 더 잘 나오지만, <b>너무 세게</b> 넣으면 안 한 말도 끼어들어요."

### tip
- body: 자막 검수는 <b>고유명사 → 숫자 → 동음이의어</b> 순서로 보면 놓치는 게 줄어요. 번역 자막은 한국어 자막을 먼저 고친 다음에 번역해요. 앞 오타가 그대로 번역되거든요.
- extra: 단어장(커스텀 보캐뷸러리)에는 자주 틀리는 낱말만 넣고, 세기를 조절할 수 있으면 작게 시작해요. 학생 실명은 클라우드 단어장에 넣지 말고 검수 단계에서 고치는 편이 개인정보 면에서 안전해요.

### myth
- myth: 단어장에 많이 넣을수록, 세게 넣을수록 자막이 정확해진다.
- fact: 단어장은 등록한 낱말 후보에 가산점을 주는 방식이라, 너무 크면 말하지 않은 낱말이 자막에 끼어들어요. 꼭 필요한 낱말만, 작은 세기부터 시작해요.
