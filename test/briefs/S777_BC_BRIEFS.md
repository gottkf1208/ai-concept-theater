## 53편 `t7-live-avatar` — 실시간으로 말하는 아바타

- 제목(가제): 실시간으로 말하는 아바타는 어떻게 만들어질까
- 부제: 실시간 영상 생성·립싱크·SynthID 워터마크
- summary: 9월 24일 Google이 Gemini 3.8 Live에 실시간으로 말하는 아바타를 붙였고, 하루 전 Meta는 목소리만으로 표정을 추론하는 통화용 홀로그램을 발표했어요. 영상을 미리 다 만들어 두지 않고 한 프레임씩 바로 만드는 인과적 생성, 입 모양을 소리에 맞추는 립싱크, 보이지 않는 워터마크가 하는 일과 못 하는 일까지 짚어요.
- keywords: Live Avatar, 실시간 영상 생성, 인과적(causal) 생성, 자기회귀, 증류, 립싱크, 판별기, 아바타, 홀로그램, SynthID, 워터마크, 딥페이크
- 의상: paris13(스웨이드·에비에이터)
- 참고 편: `v1-ai-label`(표시·C2PA), `v2-voice`(목소리 합성 기본). 이 편은 "영상이 실시간으로 만들어지는 조건", "입-소리 맞춤", "워터마크의 범위"에 집중.

핵심 주장: 보통 영상 생성 모델은 클립 전체 프레임을 한꺼번에 보며(양방향) 잡음을 걷어 내서, 끝 장면이 정해져야 첫 장면도 끝나요. 대화형 아바타는 그럴 시간이 없어서 **지난 프레임만 보고 다음 프레임을 바로 만드는 인과적(causal) 생성**이 필요하고, 큰 모델이 여러 단계로 하던 일을 몇 단계로 줄이는 **증류**로 속도를 맞춰요(2024년 연구: 50단계 → 4단계, GPU 한 장에서 초당 9.4프레임 스트리밍). **립싱크**는 소리를 입력으로 받아 입 주변을 다시 그리는 일이고, 2020년 연구는 입과 소리가 맞는지만 따지는 "전문가 판별기"로 정확도를 끌어올렸어요. Meta 홀로그램은 목소리와 말투에서 표정까지 추론해요. Google은 아바타의 모든 음성·영상 출력에 사람이 알아채지 못하는 워터마크(SynthID)를 넣었다고 밝혔어요. 워터마크는 만든 쪽이 심어 두는 흔적이라, 심지 않은 생성물은 그 검사로 잡히지 않아요.

### 만져 보기 "실시간 아바타 예산 계산기" (결정적)
- range "한 프레임 만드는 시간(ms)" 10~120(기본 30), select "화면 프레임레이트" 24 / 25 / 30(기본 30).
- 계산: 프레임 예산 = 1000 ÷ fps(ms, 소수 첫째 자리). 생성 시간 ≤ 예산이면 "제때 나와요"(aqua 테두리). 넘으면 10초 대화 뒤 밀린 시간 = (생성 시간 − 예산) × fps × 10 ms → "10초 뒤 입 모양이 소리보다 ○○초 늦어요"(주황 테두리) + 막대 2개(소리 진행 / 영상 진행).
- 결정적 예: 30fps(예산 33.3ms)에서 생성 120ms → (120 − 33.3) × 30 × 10 ≈ 26,000ms → "약 26초 밀려요". range 최대값에서 상태 문장·막대·테두리 DOM 변화 보장.
- 보조 버튼 "단계 줄이기(증류)": 생성 시간 × 4 ÷ 50(50단계 → 4단계 은유, 소수 첫째 자리 반올림) → 대부분 예산 안으로 들어옴.
- 고정 문구: "숫자는 원리를 보여 주는 예시 값이에요. 실제 제품의 속도와는 달라요."

Gemini API는 목소리 주인이 "나는 이 목소리의 주인이고 동의한다"는 문장을 직접 녹음하게 하고 참조 녹음과 같은 성인 화자인지 확인해요. ## 55편 `t7-streaming-stt` — 실시간 자막의 100밀리초

- 제목(가제): 실시간 자막은 왜 썼다 지웠다 할까
- 부제: 스트리밍 음성인식·부분 결과와 확정 결과·지연 시간
- summary: 10월 1일 Microsoft가 첫 스트리밍 음성인식 모델 MAI-Transcribe-2-Streaming을 공개하며 "첫 결과까지 100밀리초 남짓"을 내세웠어요. 말이 끝나기 전에 글자를 내놓는 스트리밍 인식, 먼저 띄우고 고쳐 가는 부분 결과와 확정 결과, 빨리 내면 자주 고치고 늦게 내면 정확해지는 맞바꿈, 언어 자동 감지까지 짚어요.
- keywords: 스트리밍 음성인식, STT, 실시간 자막, 부분 결과(partial), 확정 결과(final), 지연 시간, 첫 결과 시간, 청크, LocalAgreement, RNN-T, 언어 자동 감지
- 의상: paris15(케이프·책)
- 참고 편: `v2-subtitle`(소리 → 후보 → 가장 그럴듯한 글자, 단어장 가산점, 번역 캐스케이드). 이 편은 반복하지 않고 **글자를 "언제" 내놓느냐**만 다뤄요.

핵심 주장: 녹음 파일 자막은 말이 다 끝난 뒤 전체를 보고 글자를 정해요. 실시간 자막은 소리를 잘게 나눈 **청크**로 받으면서 **부분 결과**를 먼저 띄우고, 뒤 소리가 들어오면 앞 글자를 고친 뒤 **확정 결과**로 굳혀요. Microsoft는 첫 부분 결과가 소리를 받은 지 100밀리초 남짓에 나오고, 맥락이 더 들어오면 고쳐서 확정한다고 밝혔어요. 2023년 연구는 실시간용이 아니던 인식 모델을 실시간으로 쓰려고 "연속된 두 번의 추정에서 똑같이 나온 앞부분만 확정"하는 규칙을 썼고, 한 번에 받는 소리를 길게 잡을수록 맥락이 많아 정확하지만 늦어진다고 보고했어요(1초 단위로 받을 때 영어 평균 지연 3.3초). 2018년 연구는 처음부터 흘려 들으며 쓰도록 설계한 RNN-T 구조로 휴대폰에서 실시간 인식을 했어요. 그래서 실시간 자막의 바뀌는 글자는 고장이 아니라 설계예요. 수업에서는 띄우는 자막은 부분 결과로 빠르게, 기록·배포는 확정 결과를 사람이 검수해서 써요.

### 만져 보기 "청크 다이얼" (결정적)
- 예문 한 문장(코드 상수, 예: "오늘 사회 시간에는 지도 읽는 법을 배워요"), 낱말마다 실제 발화 시각(ms)을 상수로 둠.
- range "한 번에 받는 소리(ms)" 100~2000, 기본 300.
- 계산: 각 낱말이 화면에 처음 뜨는 시각 = 발화 끝 시각을 청크 길이 배수로 올림한 값 + 처리 시간(고정 80ms). 고침 횟수 = 청크 길이별 고정 표(100~300ms: 3회, 400~900ms: 2회, 1000~1500ms: 1회, 1600ms 이상: 0회). 화면: 위 줄 "말한 시각" 타임라인, 아래 줄 "자막에 뜬 시각" 타임라인(낱말 칩), 상태 문장 "평균 ○.○초 늦게 뜨고, 앞 글자를 ○번 고쳐요."
- range 최대값 2000에서 타임라인 칩 위치·상태 문장 변화 보장.
- 보조 버튼 "확정만 보기": 부분 결과 칩을 숨기고 확정 낱말만 잉크색으로.
- 고정 문구: "숫자는 원리를 보여 주는 예시 값이에요. 실제 모델의 지연 시간과는 달라요."

### tip
- body: 수업에 실시간 자막을 띄울 때는 학생들에게 "<b>회색 글자는 바뀔 수 있어요</b>"라고 먼저 알려 주세요. 녹화본 자막이나 회의록은 확정 결과를 한 번 읽고 고쳐서 내보내요.
- extra: 말을 문장 단위로 끊어 주면 확정 결과가 빨리 굳어요. 학생 목소리를 녹음·전사하는 활동은 시작 전에 알리고, 전사본 보관 기간을 정해 둬요.

### myth
- myth: 실시간 자막에서 글자가 바뀌는 건 인식이 불안정해서다.
- fact: 실시간 인식은 일부러 먼저 짐작한 부분 결과를 띄우고, 뒤 소리가 들어오면 고쳐서 확정해요. 기다렸다 띄우면 정확하지만 늦고, 빨리 띄우면 고칠 일이 생기는 맞바꿈이에요.

## 56편 `t7-kling4-keyframes` — 키프레임 열 개로 영상 붙잡기

- 제목(가제): 영상 중간중간에 정답 그림을 박아 두면
- 부제: 키프레임·참조 조건·사이 채우기
- summary: 9월 30일 Kling이 Kling 4.0의 세부를 공개했어요. 3~30초 영상에 키프레임 최대 10개, 참조 자료 최대 15개. 시간 축 위에 "이 순간은 이 그림"이라는 고정점을 박고 그 사이만 모델이 채우는 원리, 인물·소품 같은 참조 자료가 맡는 역할, 고정점을 몇 개 둘지 정하는 판단까지 짚어요.
- keywords: 키프레임, 시간 축, 사이 채우기(인비트위닝), 첫 프레임·끝 프레임, 참조 조건, 참조-영상 생성, 피사체 참조, 스토리보드, Kling 4.0
- 의상: paris16(화이트셔츠·메타안경)
- 참고 편: `v2-consistency`(레퍼런스 이미지로 얼굴 붙잡기), `v4-long-video`(긴 영상 드리프트), `v2-motion-prompt`(움직임 여섯 축·멀티샷), `v4-controlnet`(조건 그림). 이 편은 **"언제"를 정하는 키프레임**과 **참조 자료와의 역할 분담**만.

핵심 주장: 글 프롬프트는 무엇이 일어나는지는 말해도 "몇 초에 어떤 모습"인지는 정하기 어려워요. **키프레임**은 애니메이션 용어로, 시간 축 위 특정 순간의 정답 그림이에요. 키프레임을 박으면 모델은 고정점과 고정점 사이만 채우면 돼요. 2024년 연구는 첫 그림에서 앞으로 가는 모델과 끝 그림에서 뒤로 가는 모델을 함께 돌려, 두 고정점 사이의 움직임을 채웠어요. 공식 영상 API 문서도 첫 프레임은 주 입력, 끝 프레임은 "생성 제약"으로 넣는다고 적어요. **참조 자료**는 시간이 아니라 누가·무엇이·어떤 느낌인지를 붙잡아요. 2025년 연구는 편집·참조·마스크(가릴 영역)를 한 묶음 조건으로 넣는 구조를 냈고, 공식 문서는 참조 이미지로 인물·캐릭터·제품의 모습을 영상 내내 유지한다고 적어요. Kling 4.0은 이 둘을 크게 늘렸어요(키프레임 10개, 참조 합계 15개: 이미지 10·영상 5·피사체 7까지). 고정점이 많을수록 원하는 대로 가지만, 고정점끼리 서로 안 맞으면 모델이 억지로 이어요. 그래서 이야기의 전환점에만 키프레임을 둬요.

## 58편 `t7-guided-vision` — 카메라로 보고 말로 안내하는 AI

- 제목(가제): 카메라를 비추면 말로 길잡이를 해 주는 AI
- 부제: 멀티모달 실시간 안내·구도 안내·접근성
- summary: 10월 1일 Google이 Gemini Live에 시각장애인·저시력인을 위한 Guided Vision을 내놨어요. 카메라 화면을 실시간으로 보고 말로 설명하고, 카메라를 어디로 옮길지 안내까지 해요. 실시간 영상이 AI에게 어떻게 전달되는지, 왜 구도 안내가 핵심인지, 무엇을 맡기면 안 되는지 짚어요.
- keywords: Guided Vision, Gemini Live, 멀티모달, 실시간 영상, 프레임 샘플링, 끼어들기(barge-in), 구도 안내, 접근성, 시각장애, 저시력, TalkBack, VizWiz
- 의상: paris18(패션위크 가죽코트)
- 참고 편: `v3-multimodal`(이미지·소리·영상을 토큰으로 바꿔 한 모델이 읽는 원리, 이미지 한 장의 토큰 수). 이 편은 반복하지 않고 **실시간 스트림, 구도 안내, 접근성 설계와 한계**만.

핵심 주장: Guided Vision은 카메라 화면을 공유하면 실시간 음성 설명과 함께 카메라를 고쳐 잡으라는(reframe) 말 안내를 해요. 실시간 대화형 AI는 영상을 파일처럼 통째로 받지 않고 **장면을 일정 간격으로 떼어 낸 사진(프레임)**과 소리를 계속 흘려 보내요. Gemini 개발자용 Live API 문서 기준으로 사진은 초당 1장 이하, 소리는 끊김 없이 들어가고, 사용자가 말로 끼어들면(barge-in) 대답을 멈춰요. 시각장애인이 찍은 사진은 초점이 흐리거나 대상이 화면 밖에 걸리기 쉬워요. 2018년 연구의 시각장애인 질문 3만 1천여 건도 사진 품질이 낮고 답할 수 없는 질문이 섞여 있었어요. 그래서 "보이는 것을 설명하기"보다 **"잘 보이게 카메라를 옮기도록 돕기"**가 먼저예요. Google은 시각장애인 통역 서비스 Aira의 신뢰 테스터 1,000명 이상과 다듬었고, 이 기능은 의료기기·이동 보조기구가 아니며 길 안내·장애물 감지용이 아니라고 명시했어요. 교실에서는 라벨 읽기·물건 찾기처럼 다시 확인할 수 있는 일에 쓰고, 이동 안전은 맡기지 않아요. 카메라 공유에는 다른 사람 얼굴도 담기니 공유 범위를 함께 정해요.

### 만져 보기 "카메라 안내 받기" (결정적)
- 3×3 격자 화면(`width:100%`). 목표물 "약병 라벨"은 고정 위치(오른쪽 위 칸), 카메라 틀은 처음에 가운데 칸. 첫 상태 문장 "라벨이 화면 오른쪽 위에 반쯤 걸려 있어요."
- `button.primary` "안내 받기": 카메라 틀과 목표물의 칸 차이(dx, dy)로 안내 문장을 규칙대로 만듦. dx>0 "오른쪽으로 조금", dx<0 "왼쪽으로 조금", dy<0 "위로 조금", dy>0 "아래로 조금", 둘 다 0이면 "좋아요, 라벨이 가운데예요. 읽어 드릴게요: '하루 두 번, 식후'"(고정 문구). 안내 문장을 말풍선 목록에 쌓음(DOM 변화).
- 보조 버튼 4개(← → ↑ ↓): 카메라 틀을 한 칸씩 이동. 버튼만으로 조작해 키보드 접근 가능.
- 체크박스 "흐린 사진 섞기": 켜면 안내 전에 "사진이 흐려요. 잠깐 멈춰 주세요"가 한 번 먼저 나옴(고정 규칙).
- 고정 문구: "원리를 보여 주는 예시예요. 실제 기능은 길 안내·장애물 감지용이 아니에요."

### tip
- body: 저시력 학생과 쓸 때는 <b>라벨·학습지 글씨 읽기, 실험 도구 찾기</b>처럼 틀려도 다시 확인할 수 있는 일부터 시작하세요. 이동과 안전은 기존 보조 수단을 그대로 써요.

### myth
- myth: 카메라로 보고 말해 주는 AI면 시각장애인의 길 안내도 맡길 수 있다.
- fact: Google은 Guided Vision이 의료기기·이동 보조기구가 아니고 길 안내·장애물 감지용이 아니라고 밝혔어요. 실시간 AI는 장면을 띄엄띄엄 사진으로 받아 보고 답해서, 순간의 위험을 놓칠 수 있어요.
